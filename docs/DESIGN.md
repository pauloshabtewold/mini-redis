# Design notes

Why mini-redis is built the way it is, and where it deliberately differs from real
Redis. Split out of the README so that file stays short; nothing here is required to
run or read the code.

### Why the protocol layer works in bytes

A parser built on `str` has to guess an encoding the moment it reads off the socket, and a value that isn't in that encoding comes out corrupted on the other side. `resp.py` never makes that guess: every value in this project -- keys, values, command names, error bodies -- is `bytes`, starting from the first line of the parser and continuing through the store and the snapshot format.

### Why a bulk string's body is delimited by its declared length

A bulk string is binary-safe, which means its body is allowed to contain the exact byte pair, `\r\n`, that ends every header line in the protocol. A parser that finds the end of a body by searching for `\r\n` truncates a body that happens to contain that pair and leaves the rest of it to be re-parsed as a bogus follow-on command. `resp.py` avoids the search: a body is read as a slice at a computed offset, `buf[start:start+length]`, and the only check left is that the two bytes right after it are `\r\n`. Header lines (`*N\r\n`, `$N\r\n`) are the opposite case -- their own length isn't declared anywhere, so searching for `\r\n` is exactly the right tool for them, and only for them.

### Why a header search carries a resume position

A bulk element reports the buffer length at which another attempt can make progress, because its body's length is declared in its own header and the parser can skip straight past it. A header line has no such number: `*N\r\n` and `$N\r\n` declare their contents but not their own extent, so nothing about a partial one says when its terminator will arrive. That leaves the terminator search itself, and a search that starts at byte zero every time a caller retries is quadratic in what one connection has sent -- 64 MiB arriving in 64 KiB pieces walks about 34 GB, which is the triangular sum of 1,024 reads over a buffer growing 64 KiB at a time. The measured cost of that is worse than the same volume spent on real commands: 64 MiB of unterminated header cost more CPU than 64 MiB of pipelined `PING`s, which at 14 bytes a command is 4.8 million commands actually answered.

So the two primitives take a `search_from`, and `Connection` keeps one per connection. A search that found nothing has proved the whole buffer holds none, so the next attempt resumes at the end of what it already walked and each byte is examined once per command rather than once per readable event. The position steps one byte back from the end rather than sitting on it, because a `\r` already buffered pairs with a `\n` that has not arrived, and resuming past that pair loses the header entirely -- the connection would then hang with nothing to show for it, which is a worse failure than the cost this exists to avoid. An inline line ends at a single `\n` and has no pair to split, so it resumes at the end.

What this does not do is bound the buffer. A client can still send an unterminated line forever and the read buffer still grows to hold it for as long as it keeps sending; `--incomplete-command-timeout` ends that by time and not by size, and the entry among the deliberate differences below says what it reaches. This makes the growth cost linear rather than quadratic, which is a different fact from making it finite.

### Why Connection is a class

Keeping a raw socket in a dict keyed by its file descriptor works right up until something else needs to be tracked per connection, and several things do. The incomplete-command deadline, `incomplete_since`, is one: the server writes it as commands begin and end and reads it in a sweep, and without a home on `Connection` it would be a second dict keyed by the same descriptors and kept in step with the connection set by hand. Two more things were designed to attach state to a connection -- rate-limit tracking and a follower link -- and each would need its own parallel fd-keyed structure too. The first is built, and its window lives in the slot on the connection it counts, so there is no second table to keep in step with the connection set. The second is not built, and its slot ships with a field nothing reads, so that structure exists once instead of getting rebuilt piecemeal if it is.

### Why the three extra state slots are untyped

`rate_limit_state`, `replication_state` and `server` are all `None` until something fills them, and none of them is typed on `Connection`. `server.py` fills `server` when it registers a connection, and fills `rate_limit_state` with a `ratelimit.SlidingWindow` the first time a `client` connection sends a command while a limit is configured; `replication_state` would belong to a module that is not built and has no writer. Giving any of them a real type would make `connection.py` -- the most foundational module in the project -- import the module that defines that type, and for the other two that module needs `Connection` back: an import cycle, in the one file nearly every other module in this project eventually imports. `server.py` already imports `Connection`, which is what makes the reverse import a real cycle for the `server` slot too, not only a future one. The cycle is not a reason for `rate_limit_state`, because `ratelimit.py` imports nothing from the project. That slot has been opaque since `connection.py` was first written, before the limiter existed, and it stays so.

### Why the connection's third slot carries a narrower contract than the other two

`connected_clients` is the only one of `INFO`'s five fields that is a fact about sockets rather than about the store or the process -- `redis_version` and `role` are constants, `used_memory` is a syscall reachable from anywhere, and the keyspace line comes from the store `INFO` already receives as an argument. Two answers in this server need the server itself: that count, and `CONFIG GET save`, which reports whether a save is scheduled and how often. Reaching the server is what the third slot, `server`, exists for: filled in `Server._on_accept` once a connection is registered and tracked, and cleared in `Server._close` before the socket closes.

What sets this slot apart from the two beside it is who reads it -- a command handler, in a different module from the one that fills it. A full attribute-and-method surface would let a handler reach as deep into `Server` as it liked, which is the same category of layering violation the store's own internals check exists to catch, just outside where that check looks. The contract is written down rather than enforced by a type: a handler may read the slot's object's named public attributes and nothing else -- no method calls, no underscore-prefixed names. `Server` grows public `connected_clients` and `armed_snapshot_interval` properties rather than `INFO` reading a private `_connections` set or `CONFIG` a private save deadline, so both facts this slot exposes are already shaped as attribute reads rather than calls. The slot is `None` for a connection driven with no socket at all -- this project's own convention for in-process use -- and `INFO` answers `connected_clients:0` there and `CONFIG GET save` answers `""`, documented answers rather than fallbacks hiding a bug.

### Why select() has a bounded timeout

The periodic tasks -- sweeping expired keys, writing a snapshot -- run right after `select()` returns, never on a clock of their own. An unbounded `select()` on a server with no client traffic would simply never return, and nothing scheduled would ever run on an idle server. The timeout is bounded to keep that from happening, and it doubles as the longest a stop signal has to wait before the run loop notices it. That wait is the first part of what a stop costs and not the whole of it: the snapshot save and the drain follow, and the shutdown section below says what each costs and what bounds it. The same timeout is how late the incomplete-command sweep can notice a connection past its limit, since that sweep runs on the same tick.

### Why inline commands are supported

A bare `PING\r\n`, with no multibulk framing at all, parses as a command here, and gets a real `+PONG` back like any other reply. That's what makes `nc localhost 6379` work as a demo with nothing installed beyond what a shell already has -- point it at the port, type a command, and get an answer in the same session. `telnet localhost 6379` does the same thing on a machine that has telnet, but macOS has not shipped one since 10.13, so there it is a package to install rather than something already on the box. Quoting works the way someone typing at a terminal expects, because that's the grammar a real server applies to the same line: `ECHO "a b"` is one argument with a space in it, `'` quotes as well as `"`, `\xHH` and the usual character escapes are understood inside double quotes, and a quote left open is a protocol error rather than a literal character.

Real Redis ships a companion load-generation CLI alongside `redis-cli`, and the first workload of its default run is exactly that unframed `PING` -- 50 connections all sending `PING\r\n` with no `*`/`$` around it. Accepting inline input is what lets that workload run here at all. The tool opens by asking for two configuration values in ordinary multibulk framing, both of them in a single write, and `CONFIG GET` answers both from this server's own configuration -- neither one echoed from the reference -- so the tool goes straight on with no warning; the multibulk `PING` workload that follows works too.

### Why the periodic tasks belong in server.py

The periodic tasks belong in `server.py` rather than in `event_loop.py`, driven off the `select()` timeout: the expiry sweep and the snapshot interval are wired into the run loop. `event_loop.py` is kept to readiness dispatch alone: it knows the `Connection` class and three callbacks (`on_readable`, `on_writable`, `on_accept`) and nothing else. Putting the periodic tasks there would pull the store, persistence, the command layer, and replication, had it been built, into the thinnest module in the project.

### Why persistence reaches the store through two named methods

`persistence.py` never reaches into `Store`'s own dicts directly -- it calls `store.snapshot_items()` to read and `Store.from_items(...)` to write, and nothing else. A serializer living inside `Store` would make replication depend on the store's own internals rather than on two named methods with a fixed contract. `snapshot_items()` walks `_data` directly rather than through `live_keys()`, so a resident-but-logically-expired key is carried into the snapshot with the deadline it actually holds, rather than silently dropped the way a save reading through the expiry-aware surface would drop it. `from_items()` is a classmethod so a frozen-clock subclass loads as itself, and it reconstitutes a list value as a `collections.deque`, never a Python `list` -- `Store.kind_of()` raises `TypeError` for anything else, which closes the connection on the first list command against a store that loaded wrong rather than reporting the mismatch cleanly.

### Why the checksum covers the header as well as the entries

`persistence.py`'s CRC32 trailer is computed over every byte that comes before it -- magic, version, count, and every entry -- not only the entries a snapshot stores. Folding the count and the version into that checksum is not what keeps a flipped bit in either field from turning into a wrong-but-plausible snapshot: `decode()` already refuses one on its own, because it requires the last entry to end exactly on the trailer and reads every field either through `struct.unpack_from` or, for the one-byte type code, as a single index into the blob -- both of which raise the moment a field reaches past what the blob actually holds, where a slice would have returned short and said nothing. Measured with the checksum comparison deleted, on a fixture of three keys: all thirty-two single-bit flips of the count field are refused anyway -- two as trailing bytes left after the last entry, thirty as a bounds error inside `struct.unpack_from`. That split is a fact about the fixture and not about the format, since a flip that lowers the count leaves trailing bytes and one that raises it runs off the end: it is `popcount(count)` against `32 - popcount(count)`, so the same measurement over a two-key snapshot reads one and thirty-one. All thirty-two flips of the version field are refused as an unsupported version. What folding both fields into the checksum buys is not whether the corruption is caught but how it is named: without it, a flipped count or version still fails, but as a bounds error or an unrecognized version several fields into decoding, whichever one the corrupted bytes happened to trigger. With the checksum run first, every one of those flips is refused as corruption -- named for what it is, at the first check, before `decode()` has read enough to act on any of it -- so one error, a bad checksum, covers damage that would otherwise surface under whichever message the bytes happened to produce next. The other half of the measurement, the flips that land in a key, a value or an expiry, where no bounds check can see them and the checksum is all that stands between a flipped bit and a wrong store, is under the README's findings.

### Why the sweep is bounded by elapsed time, not an iteration count

`Store.sample_and_expire()` draws a fixed sample and reports how many of it had expired; the loop around it in `server.py` re-samples while more than a quarter of a sample came back expired, and stops on an elapsed-time budget rather than a pass count. An iteration cap looks like the safer bound and is not: it bounds dict lookups, which is not the quantity the 1 ms budget exists to protect, and if a sampling pass ever turns expensive for a reason that has nothing to do with the keyspace's own size, only a time budget still bounds the stall this puts in front of every other client on the loop. Two of the three numbers are the reference's own and one is not. Twenty keys a pass and the millisecond are compiled into both 5.0.14 and 7.2.7, at `server.h:172-174` and `expire.c:109-111` respectively. The quarter is not: there it bounds a share of a tick, where here it is a fraction of the sample a pass actually drew, and those are different quantities written with the same digits. What this sweep does with the two it borrows is its own: it draws without replacement, and it spends the millisecond on a 100 ms cadence.

Nothing more about the reference is set down here, and that is deliberate rather than an omission. Earlier versions of this section described which of the reference's two cycles each constant belongs to, how each version draws its sample and when each re-loops. Every one of those descriptions turned out to be wrong in some clause, each correction introducing the next, and none of them was load-bearing: this server behaves identically whatever the answer is. The two constants above are checkable against the tagged sources named; the machinery around them belongs to the reference and is documented there.

### Why the snapshot blocks the loop

Serializing the keyspace and writing it out happens on the one thread that answers commands, so for the length of a save the server answers nobody. Real Redis forks and lets a copy-on-write child pay that cost, which is the right answer at scale and the one given up here: every non-tearing alternative needs a point-in-time view of the keyspace. Chunked serialization that yields every N keys has none -- a write lands mid-save, and the file decodes cleanly into a keyspace that never existed. A pure-Python copy supplies one more cheaply than it sounds, because values are immutable `bytes` that a shallow copy can share: copying 100,000 string keys, 16-byte keys with 100-byte values, added about 5 MiB to peak resident memory by `ru_maxrss` -- about a third of what those keys and values occupy themselves -- and took about a millisecond. But every list has to be copied element by element, and the encode would still run on this one thread, spread across many ticks instead of one; this design takes the single pause instead. So the pause is priced rather than hidden: it is measured on a stated fixture and published in README.md, and `--snapshot-interval` is the one control over how often a client meets it. It is also why the sweep next door is held to a millisecond and the save is not. The sweep runs many times a second by default and a stall there sits in front of every client all day; a save is rare, bounded by the size of the keyspace, and the thing that makes a restart survivable at all.

### Why the save fsyncs the directory as well as the temporary file

The rename is what makes a save atomic, and on its own it already covers the failure a reader pictures first: a process killed mid-save loses nothing already written, because the bytes a `write()` call hands to the kernel sit in the page cache and outlive whatever killed the process. What the rename does not cover is power loss, where the temporary file's data and the directory entry the rename creates are two separate writes the drive is free to commit in either order. Both orders lose something, and they lose different things. A cut that keeps the data and loses the entry leaves the directory still naming the old snapshot, with the new file's bytes on disk and nothing pointing at them: the previous snapshot, intact. A cut the other way is the one that bites -- the entry naming the new file is durable and the file's own bytes are not, so the real snapshot path names a short or empty file, which is what the sync *before* the rename exists to rule out and why that sync is not merely about the drive's cache. And the drive's own cache can have acknowledged neither: a plain `os.fsync()` returns once the drive says it has the write, which on macOS is not the same as the write having left the drive's own cache, so the same cut can still lose data `os.fsync()` already reported as safe. Closing the first gap means fsyncing the snapshot's directory after the rename runs, not only the file before it. Closing the second means asking for more than `os.fsync()` promises where the platform offers a way to: `fcntl(fd, F_FULLFSYNC)` on macOS, which forces the drive to flush its own cache, falling back to a plain `os.fsync()` where the call is unavailable or the filesystem refuses it. A filesystem that refuses to sync a directory at all is tolerated rather than failed, because the rename has already put the new snapshot in place by the time that sync runs, and refusing the save over a guarantee the rename no longer needs would trade a working snapshot for none.

None of this is free. A device flush is the one step in a save that waits on the drive rather than on the kernel, and it falls inside the same pause the encode already blocks the loop for. Measured on the fixture the figures above are taken on -- 16-byte keys and 100-byte values, alternating the two forms of the sync pair by pair so that drift falls on both -- it costs about 6 ms on a snapshot holding a single key, where there is almost no writing for it to wait on, and about 12 ms at 100,000 keys, against 71.7 ms for the same save without it. The second of those is the least steady figure in this document, and it is worth saying why rather than publishing it as though it were not: a device flush waits on the drive and not on this process, so it is the one measurement here that a busy machine inflates rather than merely blurs -- over repeated runs its upper quartile has read nearly twice its median, where the one-key figure holds to within a millisecond. A drive that ignores the request pays neither, and reports the same success. What keeps the cost affordable is what keeps the pause affordable: it is paid once per `--snapshot-interval`, not once per write. The three figures in this section are published here, and the README, which prices the pause itself, does not repeat them.

### Why a stop saves first and drains second

On `SIGINT` or `SIGTERM` the loop stops, and three things happen before the teardown, in a fixed order: the listening socket leaves the select set, a snapshot is saved, and the server spends up to `--shutdown-drain-timeout` seconds waiting to send the replies already queued for its clients, a deadline that neither the sweeps of the accept backlog inside the drain, nor the reads that empty and count the receive queues, nor the flush the teardown makes as it closes each connection is under, as the paragraphs below say. The listener is only unregistered at first, and the socket itself stays open until the teardown: leaving the select set is what stops anything further being served, and keeping the socket is what stops a replacement server binding the port while this process is still running. A connection that arrives in between completes its handshake in the kernel's backlog and is never served: the drain accepts it only to ask what it holds and then closes it, and it is never registered, tracked, counted by `connected_clients` or dispatched to. Of the clients swept this way, one that had sent bytes sees the same reset the listener's close would have given it, and an idle one sees an orderly close instead. The save comes before the drain because the two have different bounds. A save costs what the keyspace costs and no client can lengthen it; a drain costs what its slowest reader costs, and a client that never reads holds it to the whole timeout. An operator who has waited long enough to give up and send `SIGKILL` must not find that the snapshot was the thing still waiting behind a reader that was never going to read. The save runs whether or not `--snapshot-interval` is `0`, bar the one pairing described below, because that interval schedules periodic saves and a save on the way out is not one. The consequence is stated rather than hidden: `--snapshot-interval 0` on its own does not mean the file at `--snapshot-path` is never written, only that nothing writes it on a timer, and `CONFIG GET save`, which reports the schedule, answers `""` from a server that will still save when it is stopped. One pairing is excepted on purpose: `--ignore-snapshot` with `--snapshot-interval 0` skips the save on the way out as well, and the file at the path is left exactly as it was. That flag is the escape hatch for a snapshot that refuses to load, so the file is what is being rescued, and with periodic saving off the stop is the only thing left that could write over it; a save there would turn the escape hatch into the way the file is destroyed. The startup path follows the same rule when it names a stale temporary file beside the snapshot and removes nothing, because that file may hold the only copy of a newer save. Every other pairing saves on the way out: `--snapshot-interval 0` alone, and `--ignore-snapshot` with a non-zero interval, where the next interval would overwrite the file anyway. A save that fails is reported through the same bounded boundary a periodic one is, and the drain and the exit go ahead.

What the drain does with inbound bytes is the part that is easy to get wrong. The obvious design stops reading once the drain begins, and it looks right because it is what keeps the work finite: nothing new arrives, so nothing new is queued, and the loop only has to wait for what is already owed. But a request left unread in a socket's receive queue turns the close that follows into a reset instead of an orderly shutdown, and a reset discards the closing socket's own send queue: the bytes this process handed to its kernel that the kernel had not yet put on the wire. It does not take back what the peer had already received -- measured, a client reads every byte that had been delivered and meets the reset only on the read after the last -- so what goes missing is the tail that never left the server, which for a slow reader is the last of the replies the drain was waiting to deliver. A client with one request in flight would lose replies that `send()` had accepted. So the drain keeps reading, and what bounds it is that nothing is dispatched: no command runs, so no reply is queued, so the quantity owed only ever falls, while the bytes that arrive are read and thrown away and the receive queue is empty when the close comes, which makes the close orderly and leaves the kernel to finish sending what it holds. A command dispatched during the drain would also be a reply for a write the snapshot has already missed. Read interest is switched on for every connection that owes bytes when the drain begins, and does not last the drain for every one of them. The switching on is for a connection the high-water mark had paused: outside the drain nothing else clears read interest on a live connection, because end of input outside the drain closes the connection instead of holding it, and a paused connection has requests unread in its receive queue. Left unread through the whole drain, those requests would make the close that ends it a reset, with the loss described above. The call changes nothing for a connection already being read, and it cannot leave one with an empty mask, because every connection it is made for owes bytes and write interest follows that. After it, end of input on a connection that owes bytes clears read interest, as described below, which leaves that connection registered for writing only, and once its buffer empties the write bit goes too, the mask reaches nothing, and the applier unregisters it, because the selector spells an empty mask unregistered and the applier never asks it for one. That is intended: the connection is still open and still in the set until the teardown closes it, it owes nothing, and nothing about it needs to wake the loop. The drain loop is the event loop's `run_once()` on its own and not the main loop's pairing of it with the periodic tick, because a tick would run the expiry sweep, whose deletions after the snapshot are writes no snapshot holds, and a periodic save inside a stop that has already saved. A connection that owes nothing when the drain begins is closed before the first pass.

End of input is handled by the same question, what would the close discard. A client that has shut down its sending half is finished asking and still reading, but end of input is also how a dead peer looks, and outside the drain the read path takes it for one: it closes the connection and discards everything queued for it after one best-effort flush, as the reference does. During the drain that would close exactly what the drain exists to deliver, so end of input on a connection that still owes bytes does not close it. Reading from that connection stops instead, because end of input stays readable and a connection left registered for reading would be reported ready by every `select()` for as long as the drain ran, and what it owes goes out until it is drained or the deadline arrives. A peer that has really gone makes the next send fail, which `_flush` answers with a close the drain then counts as a loss, and a peer that has stopped reading is held by the deadline like any other. End of input on a connection that owes nothing still closes it, because there is nothing queued for the close to discard and nothing unread to turn it into a reset.

The timeout plus one `select()` timeout bounds the part of the drain that waits on connections, because the deadline is read between passes of the loop and a pass that starts shortly before it still runs to its own timeout. The two sweeps of the accept backlog described below sit outside that bound: they run at the drain's entry and in its `finally`, with no deadline of their own, and what ends a sweep is `accept()` finding nothing pending at the instant it polls, so the kernel's backlog does not bound it and a client that keeps connecting can keep it going. With nothing connecting during it, a sweep accepts what the backlog held, which was 128 when the backlog had been filled to `SOMAXCONN`, and did so in 1.3 to 3.1 ms over 3 trials; with clients connecting continuously one sweep accepted 722. Measured over 58 sweeps timed inside `_count_unaccepted_backlog` in runs where clients connected after the stop, they took 0.005 ms to 383.3 ms with a median of 0.9 ms, 14 of the 58 under 0.2 ms and 6 over 28 ms, all six in runs of continuous connectors. The drain and sweep figures in this section were measured on macOS loopback at a load average of 2.9 to 7.0, and the sweep and exit times are a function of that and of how many clients are connecting. This matters at `--shutdown-drain-timeout 0`, where four steps between the loop stopping and exit have no deadline: the sweeps, the snapshot save, which this flag does not limit either, the reads that empty and count the receive queues, described below, and the flush that `_shutdown`'s per-connection `_close()` makes. That flush is `Connection.flush()`, a loop of `send()` calls that runs until the kernel refuses or the buffer is empty, once for each connection still owing bytes, up to `--max-connections` of them, and it runs after the drain has written its one line. Measured at `--shutdown-drain-timeout 0` with 150 connections each owed one 1,048,588-byte reply, 157,288,200 bytes in all, and readers that began reading only after the signal, 63,918,688 to 143,578,892 of those bytes were handed over after the stop over 11 runs, 40.6% to 91.3% with a median of 50.3%, SIGTERM to exit taking 0.052 to 0.278 s; with nobody reading, none was handed over. A client that keeps connecting can extend the sweeps on this host: with 4, 7 and 32 processes connecting continuously at `--shutdown-drain-timeout 0`, over 8, 8 and 6 runs at a load average of 4.8 to 7.0, the longest sweep took 139.0, 363.9 and 383.3 ms, against 1.3 to 3.1 ms for a full backlog with nothing arriving, and SIGTERM to exit took 0.040 to 0.420 s over the 22 runs, median 0.085, the longest at each count 0.1923, 0.4181 and 0.4199 s. `--shutdown-drain-timeout 0` reads the opposite way from the limit flags it sits beside. On `--write-buffer-limit`, `--max-value-size`, `--max-multibulk`, `--max-connections`, `--rate-limit` and `--incomplete-command-timeout`, `0` removes a limit, so a check that closes or refuses something stops doing it and disabling it is permissive; here the value is a time allowance, and `0` is no time at all, which is no drain pass: the drain's setup pass and the two sweeps of the accept backlog still run, so what a connection was holding is still counted and a client waiting in the backlog is still swept, but no pass reads anything, and every connection that owes bytes gets the single best-effort flush its close attempts and nothing beyond it. `--port 0` and the two intervals are not counterexamples to that reading, only different readings of their own -- the kernel chooses a port, a periodic task is switched off -- and none of the three is a limit that `0` removes, or restrictive. The two water marks have readings of their own as well: `--write-buffer-high-water 0` disables the pause, and the low-water mark beside it is then unreachable, which is accepted and not refused; with the pause on, `--write-buffer-low-water 0` means resume only when the queue is empty, the most conservative resume and not a way of switching anything off. The inversion is deliberate and it is the sharpest edge in the flag set, because an operator who reads the limit flags correctly and generalises will set this to `0` expecting an unbounded drain and lose whatever was queued on every restart. Nor is the loss only the part the one flush could not hand over: no read pass runs at `0` either, so a request that arrives at any point after the main loop's last pass, which includes the whole of the snapshot save, is never dispatched. It is not left to be reset, though, because the receive queue is read and thrown away and counted before the close, by the close of a connection that owes nothing and by the survivor walk for one that owes bytes; the gap section below says what that leaves. The drain ends with exactly one log line however it ended, a pass that raises included, because the line is written from a `finally`. It carries two counts of replies, because a loss of replies has two shapes: connections closed while they still owed bytes, whether a peer that went away, the write-buffer limit or an unhandled error closed them, and connections still owing bytes when the deadline arrived, a count taken before the teardown's flush hands those connections what the kernel will take, so it is an upper bound on the connections that lose a reply and not the number that do: in each of the 11 runs measured above the line read `incomplete` with 143 to 146 connections still owed bytes, and 40.6% to 91.3% of the queued bytes were delivered after it. It carries a third figure for requests, the inbound bytes the stop threw away without dispatching them, which is the only report there is of the writes a stop throws away and which is largest for a connection the high-water mark had paused, whose whole pipeline is sitting unread. It counts them in all five shapes they arrive in, because a figure covering only one of them reports 0 in the cases that matter most: what was in a read buffer when the drain began; what a half-received command had already had parsed off that buffer, which a connection holds with the buffer empty, so that the buffer's length alone reports 0 for it -- measured, 1,400,019 bytes of one `MSET`; what the drain read and discarded while it ran; what was still in a connection's receive queue when that connection was closed or the drain ran out of time; and what sat on the connections the kernel completed into the accept backlog after the stop, which are never served, and which are swept twice because one sweep missed every client that arrived during the drain -- measured, 201,000 bytes from three such clients, counted exactly in 4 of 4 runs and reported as 0 in 3 of 3 runs without the sweep. The receive queue is the shape that is easy to miss and the one that dominates -- the drain ends as soon as no connection is owed a reply, and at `--shutdown-drain-timeout 0` it ends before a single read, so a count of what the drain read reports nothing at all for a pipeline of fifty thousand requests. The receive queue is counted by reading it off the socket and throwing it away, under a ceiling that the kernel's own `ioctl` supplies. The reason is a precaution, not a fault observed in the server. The ioctl's answer might not be additive with the drain's reads: a kernel that walked the receive queue summing each queued buffer's whole length would answer for the part of one buffer that an earlier `recv()` had already taken, and that part is exactly what the drain's read path counted when it took it. No kernel available to this project was seen to answer that way. Measured over 120 trials, two kernels by two socket families by three send shapes by ten, the ioctl plus what had been read came to exactly what had been sent, an over-report of 0 bytes in all 120, and 308,992 appeared in none of them. That figure is the value a CI assertion printed when it failed, on a test that sent 280,000 bytes over a `socketpair`, and the mechanism behind it is inferred from arithmetic and from the size of a kernel buffer and was not observed. If the buffers hold 36,544 bytes, one `recv()` of 65,536 bytes takes the first whole and 28,992 bytes (65,536 - 36,544) of the second, and a kernel that then counted the second in full would answer 243,456 (280,000 - 36,544) where 214,464 bytes (280,000 - 65,536) remain; 65,536 + 243,456 is 308,992, which is 28,992 over the 280,000 sent. A 280,000-byte pipeline fills at most eight such buffers, seven holding 255,808 bytes and the eighth the other 24,192, so the twelve buffers below belong to a different measurement. That one was taken on Linux over a `socketpair`, which is `AF_UNIX` there: one non-blocking `send()` of 10 MiB was accepted 438,528 bytes at a time, which is twelve 36,544-byte buffers exactly, and the same 438,528 was accepted from a requested send buffer of 204,800 bytes upward, a 2 MiB request being granted 425,984, so it is not the size of any send buffer the kernel reported. On macOS the same call accepted 2,097,152 bytes, 30 of 30, 4.78 times as many, so neither figure holds on the platform the rest of this section was measured on. Every socket this server opens or accepts is `AF_INET`. Reading the kernel source of Linux 6.8, 6.17, 6.18 and the development tree, a TCP socket's figure is the difference of two sequence numbers, exact in all four, and the whole-buffer sum is found only in the `AF_UNIX` stream path, present in 6.17 and 6.18 and fixed upstream. So the double count belongs to the test's `socketpair` and not to a connection this server accepts, and the read stays because the count is right whichever way a kernel answers, not because the server was seen to over-count. Reads cannot find bytes that are not there, so what the read reports is right whichever way the kernel answers, and the ceiling is what keeps the loop bounded against a peer that goes on sending while it runs. Where nothing has ever read the socket the ioctl is the answer rather than a ceiling, because every buffer on the queue is whole and a kernel that sums whole buffers and one that sums only the unconsumed part cannot disagree: that is the accept-backlog sweep's case, and it is the one site that still asks. It counts with the bare ioctl and closes the socket unread, so what it counted is not emptied and a client that had sent bytes sees the reset: measured, 1,400 bytes were counted and not emptied, and the sender saw a reset. The read costs in proportion to the bytes queued where asking cost in proportion to the connections open, at a point in the stop that no deadline covers, which makes it a fourth such step: it ran at 1.84 GB/s, and a stop of 400 connections with 52 MB queued took 0.04 to 0.19 s against 0.04 to 0.075 s before the read, a difference inside the run-to-run noise of this host. No worst case was measured, so none is stated. What that count cannot see is what the **peer's** own kernel still holds unsent, which is not a question this server can put to anyone: `FIONREAD` answers for this socket's receive queue and nothing reaches past it. How much the peer still held depends on how long the drain lasted, which the client decides as much as the timeout does. A client that never reads holds the drain open for its whole timeout, and the peer delivers inside it: 0 bytes uncounted in 23 of 23 runs at `--shutdown-drain-timeout 5`. `_drain_for` itself, start to finish, took 5.0042 to 5.1001 s over 12 further runs instrumented from inside the process, median 5.0949, with the pause edge seen in each; the timeout plus one `select()` timeout is 5.1 s, so the longest ran 0.1 ms over it, which the setup pass and the two sweeps, outside that bound, are enough to account for. SIGTERM to exit, which adds the loop noticing the signal, the save and the teardown, took 5.0287 to 5.3570 s over all 35 runs, median 5.223. A client that reads its replies ends the drain as soon as no reply is owed -- `_drain_for` took 0.1 to 0.3 ms over 17 runs, and SIGTERM to exit 0.021 to 0.079 s, median 0.046, not five seconds -- and whatever its kernel still held is uncounted: non-zero in 8 of 17 runs, 110,822 to 515,628 bytes with a median of 380,328 over those 8, the same 8 of 17 that an earlier measurement of this shape gave, and every one of the 17 reported under an INFO line reading `complete`. At `--shutdown-drain-timeout 0` there is no read pass, and the uncounted amount is what the peer's own send queue still held, which was usually nothing. Measured with a client that never reads, over 39 runs of a 1,588,890-byte pipeline in three harness shapes, it was non-zero in 10, with a maximum observed of 581,164 bytes, 36.6% of the pipeline, and a median of 515,628 over those 10. The shape decides it: 0 of 15 when the client's push had completed before the stop with the pause armed, 1 of 12 with the pause armed and the stop landing mid-push, at 293,582 bytes, and 9 of 12 with the pause off and the stop mid-push, at 45,498 to 581,164. It is usually zero because by the time the drain's `finally` runs the client has usually handed the server's kernel everything it was going to send, and its own send queue is empty. These runs were taken while the survivor walk still asked the kernel with `FIONREAD`, which on macOS loopback answered with the whole 1,588,890 bytes although `SO_RCVBUF` was 408,300, the receive queue overcommitting; the walk now reads the queue off instead. Where it was non-zero, the figure equalled `SO_NWRITE`, the byte count of the client socket's own send queue read after the exit, in 9 of the 10 runs, and the tenth differed by exactly 8,192 bytes; on a 9,533,340-byte pipeline it was exact in 3 of 3, at 638,508, 532,012 and 843,308. **The largest values observed are not a ceiling**: the uncounted amount is whatever the client's send queue still held at the stop, which a longer pipeline raised to 843,308 bytes, and it cannot exceed what the client sent. The requests figure does not move the level, and the reason is not that the bytes of a half-sent command and of a whole discarded request are always indistinguishable. `has_incomplete_command` answers for bytes in a read buffer and for a multibulk held with the buffer empty, which are the first two of the five shapes; it cannot answer for the receive queue, the shape that dominates, because the bytes in a kernel receive queue were never parsed. So the two kinds are distinguishable where they have been read and not where most of them are -- and even where they can be told apart, no threshold separates them by size, which is the argument that carries: a command only half sent leaves its bytes in a read buffer too, and one client caught mid-upload holds more of them than a whole discarded pipeline. Measured, 4,194,334 bytes in 4 of 4 runs for one client caught mid-upload of a declared 8 MiB value after sending a 4 MiB body, 20 consumed and 4,194,314 buffered, against 1,588,890 for fifty thousand pipelined `SET`s. The pipeline is bounded by what the client sent. What bounds the upload is not `--max-value-size` alone, because `consumed_for_incomplete_command` counts a multibulk's header and finished elements as well as the element arriving, and it is not `--max-multibulk` times `--max-value-size` either: each element brings its `$<length>\r\n` prefix and its `\r\n` terminator and the command its `*<count>\r\n` header, none of which is in the product, so with both flags set the bound is the product plus that framing, 8 bytes an element at `--max-value-size 100`, and the header, less the byte that would complete the command. Measured at `--max-value-size 100` with all but the last element of a command finished and 50 bytes of the last, 276, 384, 600, 1,033 and 10,754 bytes were held and reportable at `--max-multibulk` 3, 4, 6, 10 and 100, against products of 300, 400, 600, 1,000 and 10,000 -- under at 3 and 4, equal at 6, over by 33 at 10 and by 754 at 100 -- and bounds of 327, 435, 651, 1,084 and 10,805. A threshold above the pipeline misses the pipeline; one below it warns on an ordinary upload. What a structural discriminator could still do is separate the connections the pause had stopped reading: the drain's setup pass calls `set_read_interest` for each connection that owes bytes, having abandoned the ones that owe nothing first, and the return value, which says whether the registration changed and so whether the pause had stopped that connection's reading, is not currently kept. A paused connection always owes bytes, because the pause is lifted as soon as its queue empties, so the connections the pass abandons were never paused ones. Keeping it would be a second counter and a fourth number on the line rather than a change of level. The word on the line is therefore about replies alone -- `complete` means every connection that was owed bytes got them, not that nothing inbound was thrown away -- and both halves have to be read. Either reply count being non-zero makes the line a warning and both being zero makes it informational, so a stop that lost replies says so at any level that shows warnings, while a stop that lost only requests says so in the figure and at INFO. The informational line is shown at the default level, INFO, so a stop that handed everything to the kernel ends with one line saying so; `--log-level WARNING` leaves only the warning. Only connections that owed bytes when the drain began are counted **by the two reply counts**: one that owed nothing is closed before the first pass and has no reply to lose. It is not outside the third figure, which counts what every connection the stop disposes of was holding, the ones it abandons for owing nothing included -- the gap section below says what such a connection is still exposed to. A negative value and one above `2**63 - 1` are both refused, at the CLI and by the constructor. That ceiling is this project's own convention for the largest value anything here may hold, and it sits far below where the arithmetic actually fails, which is where a float stops being able to hold the sum, around `10**308`; it is there so that a value that large is a one-line refusal at startup, like every other bad value, and not an `OverflowError` on `SIGTERM`, after the save. A second stop signal while the drain runs changes nothing: the handler only clears the flag the loop has already left, so ending the drain sooner is the timeout's job, or `SIGKILL`'s.

One gap is left, and it is a limitation of this design rather than a corner of it. A client that is still sending when the drain ends can lose the tail of its replies. The drain is over the moment the last owed byte has been handed to the kernel, which on loopback is long before a slow client has read it, and handed to the kernel is not the same as on the wire: the kernel can still be holding the tail of it, unsent. A request that arrives after the drain's last look at the receive queue is still there when the connection closes, so the close resets it, and the reset discards what the kernel was holding. That last look is the survivor walk in the drain's `finally`, which empties what it counts, so the window is between that walk and the close rather than after the last read pass; `README.md` carries the runs that measured the difference. What the peer had already received stays received, and the loss is that tail. With `--shutdown-drain-timeout 0` there is no read pass at all, so for a connection that owes bytes the main loop's last pass and the survivor walk are the only two reads there are, and a request that arrives between them -- which includes the whole of the snapshot save -- is read by the walk and counted rather than left for the close to reset. A connection that owes nothing when the drain begins is closed with no read pass at all, and its close reads the receive queue for the same reason the walk does: its own buffer is empty, but the kernel may still hold bytes an earlier send handed it, and those are counted and taken rather than reset away. A client that sends and then stops loses no reply tail this way, because by the last pass every reply it is owed has been handed over or counted as lost -- but it is not unaffected, since every request the drain read and discarded, and every request still in its receive queue at the close, was a write it had already been told had left. That is the cost the water marks section prices, and the drain's third figure is where it is reported. Closing the gap completely needs the close to wait, and a half-close on the server's own side is not a way of waiting: measured on a pair of sockets with a request unread and replies still held by the kernel, `shutdown(SHUT_WR)` followed by a close lost as much as a close alone, and both ended in a reset at the client, because the reset is sent when the receive queue is not empty at the close, whatever was done to the send side first. Two waits do close it, and each lost nothing in the same setting. One holds the close until the kernel's own send queue for the socket has emptied, which is a question this server does not put to the kernel, is platform-specific, and would tie the exit to the pace of the slowest reader for as long as the deadline allows. The other half-closes and then holds the close until the peer's own end of input arrives, which needs the client's cooperation and has no bound but the deadline against one that never gives it. This server does neither, so reading and discarding narrows who can be hurt to a client that is still sending, and does not remove them. The half-close a client makes is a different case, and the drain honours it, as described above.

### Why commands is a package

The command layer covers twenty-six commands across the string, list, and server/connection groups, each with its own arity check, type check, option parsing, and effect return. A single `commands.py` holding all of that would be a god object, so the command layer is split by type into its own package instead, with `registry.py` handling registration and dispatch.

### Why the kind tag is declared at the handler

A command's `read`/`write`/`other` tag is set through the same decorator that registers it, in `commands/registry.py`, rather than listed in a separate table somewhere. A table is a second place that can disagree with the handler it describes -- whatever reads the tag reads whichever one it was pointed at, and a command mistagged in the table looks correct at every other call site. Declaring the tag where the command is registered means the declaration and the handler are the same statement, so the two can't drift apart; an enum on top of that turns a typo in the tag into an error at the line that has it, instead of a value that silently matches nothing. Nothing in the server reads the tag: the rate limiter counts every command whatever its kind and exempts by the connection's role, and replication is not built, so the only reader is the test suite.

### Why one lookup answers every existence question

`Store.lookup()` is where a handler asks whether a key is there, and every handler that needs to know goes through it -- `SET`'s `NX` and `XX` conditions, `INCR` and `DECR`'s read-modify-write, every type check made by passing `kind=`, and every plain `GET` besides. A key past its deadline is deleted the moment this call finds it and reported as absent from there on, so the answer is the same no matter which handler asked or why. A raw `key in self._data` written anywhere else would skip that deletion and answer a question this server has already decided differently, with nothing downstream ever told the two disagreed. `DBSIZE`, `KEYS` and `INFO`'s keyspace line are the one deliberate exception to this rule, covered below.

### Why a list value is a `collections.deque`, never a Python `list`

`LPUSH` and `LPOP` both act on the head, and a Python `list` is O(n) per head operation because every remaining element has to shift down to close the gap. Measured on macOS: `list.insert(0, x)` at n=100,000 costs 50.90 microseconds, `deque.appendleft` costs 0.02 microseconds, and one whole `SET` through this server's own dispatch costs 0.70 microseconds -- so implementing the head push the `list` way would cost as much as 73 entire command dispatches at that size alone, growing without bound as the list grows further, against a `deque` push that stays a small fraction of one dispatch regardless of size.

The trade is not free, and the cost is visible on the other side of the same choice: `LRANGE` reads through `itertools.islice`, and `islice(deque, 0, 600)` measures 3.69 microseconds against 0.76 microseconds for the equivalent `list` slice -- a 4.9x constant factor on a command the standard benchmark invocation runs four times, at ranges of 100, 300, 500 and 600 elements. That constant factor is the part of the cost bounded by the length of the range. The rest is the seek, and it is not bounded by anything: `islice` only ever starts at the head, so reading the same 600 elements off the far end of a 400,000-element `deque` measures 887 microseconds against 3.45 at the head, where the `list` slice measures 0.66 at both because it does not seek at all. Left there, `LRANGE k -1 -1` -- a range of one element, and the ordinary way to read a list's last -- would cost the whole length of the list on a loop with one thread to spend. What makes the trade come out is that a `deque` walks from either end at the same cost per step, so `lrange` reads the half nearer the tail backward off `reversed()` and turns the run round again. The seek is then the distance from whichever end is closer: `LRANGE k -1 -1` is flat in the size of the list, and only a range landing at the exact middle pays n/2 -- which is what the reference's own quicklist pays there too. The push-side penalty a `list` would carry has no equivalent escape, because a head insert moves every element behind it whichever end the walk started from. A `deque` does give up O(1) random indexing, and that single-element read off the tail is the one shape which would have wanted it; reading from the nearer end is what stands in for it.

### Why `DBSIZE`, `KEYS` and `INFO` are the one path that bypasses `lookup()`

Routing any of the three through the expiry-aware `lookup()` fails on two separate grounds: it would turn an O(1) count into an O(n) scan, and it would have a read command delete every expired key it happened to scan past, queuing a `DEL` for each -- a count, a listing or a report mutating the keyspace it was only asked to describe. Only one of the two problems can be fully solved: any filter that answers correctly has to inspect every deadline, so `DBSIZE` cannot stay O(1) and also filter. What it gets instead is the cheapest available correct answer -- `len(_data)` minus the count of already-passed deadlines in the expiry index, which is linear in the number of keys carrying a TTL rather than in the keyspace as a whole, so a keyspace with few TTLs stays cheap however large it grows. `KEYS` is linear in the keyspace regardless, because it has to return every key that matches. All three live on `Store` itself -- `DBSIZE` and `INFO` both read `live_count()`, `INFO` alone also reads `expiring_count()` for its `expires=` figure, and `KEYS` alone reads `live_keys()` -- rather than as license for the command layer to read `_data` directly -- no module outside `store.py` touches it, and this exception is no different.

### Why `KEYS`'s glob is hand-written rather than `fnmatch`

The two were measured side by side on the same nine patterns against the same key sets -- the reference over the wire, `fnmatch.fnmatchcase` in this interpreter -- and they disagree on four. Three of the four are exact opposites of each other: `^` negates a character class on the reference and is an ordinary member of the class under `fnmatch`, and `!` is the reverse. A client asking this server for the complement of a set would, under `fnmatch`, receive exactly the set it meant to exclude -- the complement of the complement -- with no error anywhere to notice by. The fourth disagreement is backslash escaping: `fnmatch` has none, so `a\*b` matches `a*b` on the reference and matches nothing under `fnmatch`. One further problem stands on its own regardless of what the reference does: `fnmatch` memoises every translated pattern in a cache that lives for the process and is keyed by whatever a client sends it.

That argument settles which matcher to write and settles nothing about whether the one written is faithful, and choosing patterns by hand cannot settle it either -- a hand-chosen case tests the grammar the author already had in mind. What settles it is a differential fuzz: 510,000 random `(pattern, key)` pairs across three alphabets, each pattern asked of `redis-server` 7.2.7 over the wire as a `KEYS` and of `_glob_match` in this interpreter, with any disagreement printed. Two escaped every hand-written case and both fell out of the fuzz immediately. The first is signedness. The reference walks its pattern and its key through `char`, which is signed on the platforms this is measured on, so `0xff` reads as `-1` and a class range orders its endpoints on that reading -- `[\x00-\xff]` is the inverted range `-1..0` and matches almost nothing, where the obvious unsigned port makes it match everything. A range wholly below `0x80` or wholly above it behaves identically either way, which is why only a range straddling `0x80` can show the difference, and why nothing chosen by hand had. `_signed()` exists for that one comparison; equality needs no such thing.

The second is where `KEYS *` gets its answer. The reference's matcher refuses every pattern against an empty key except the empty pattern, `*` included -- its loop is `while (patternLen && stringLen)` and never runs. `KEYS *` still lists an empty-string key there because `keysCommand` short-circuits the exact one-byte `*` before the matcher is reached at all. Reproducing the visible behaviour by making the matcher itself accept `*` looks equivalent and is not: it makes every longer run of stars accept too, so `KEYS **` diverges. The short-circuit belongs in `keys()`, where the reference keeps it, and the matcher stays faithful underneath.

### Why deadlines are wall-clock and durations are not

`Store.now_ms()` reads `time.time()`, not a monotonic clock, and every deadline in `_expiry` is milliseconds since the Unix epoch -- what `PEXPIREAT` hands the store directly, and what `EXPIRE` and `PEXPIRE` convert their durations into before `_apply_expiry` ever sees them. A deadline two machines can agree on has to be a timestamp both read the same way, which is what a monotonic clock cannot offer: it reads faster and never jumps, but what it counts is an offset from an epoch that means something only to the process that started counting. A deadline recorded against that offset means nothing to a second server, or to this one after a restart, and the corruption stays invisible until exactly that moment. Every duration in this server -- the sweep interval, the snapshot interval, the rate-limit window -- is measured the other way, through `time.monotonic()`, because what they bound is elapsed time on this one process rather than an instant two processes have to agree on.

### Why the integer grammar is hand-written

`parse_int64` checks a field byte by byte before it ever calls `int()`, because `int()` accepts several shapes the protocol does not: a leading zero (`011`), surrounding whitespace (`" 5"`, `"5 "`), an explicit sign (`+5`), a digit-group underscore (`1_0`), and a negative zero (`-0`) all parse cleanly under `int()` and are all refused here. The gap isn't cosmetic on the one path where a stored value comes back through this function: `INCR` and `DECR` reinterpret whatever `SET` last wrote as an integer, and left to `int()`, a stored `"011"` reads back as `11` and `INCR` hands back `12` -- silently accepting, on the way out, exactly the string real Redis refuses on the way in.

### Why a past-dated expiry deletes rather than schedules

`EXPIRE`, `PEXPIRE` and `PEXPIREAT` all resolve to an absolute deadline before `_apply_expiry` acts on it, and a deadline at or before now deletes the key on the spot instead of being written into `_expiry` for a later lookup -- or a later sweep pass -- to clean up. The two look identical here -- either way the key reads as gone -- and what differs is what stays behind. A past deadline left in the index keeps the key resident, carried with that deadline into any snapshot taken before something reaches it, and a follower has no license to remove a key on its own initiative: only the leader's own `DEL`, or a `FLUSHALL`, grants it one, and that `DEL` goes out only when the leader's next lookup reaches the key or a sweep pass happens to sample it. A key nobody asks for waits on a sweep that promises nothing about when it reaches any one key, and with `--expiry-sweep-interval 0` never reaches it at all. Deleting on the spot ships the `DEL` with the command that caused it, so a follower is never left holding a key its leader has already stopped considering real.

### Why a reply and its effect are different facts

A handler here returns reply bytes and a list of effects -- `Reply = tuple[bytes, Effects]` -- and every handler returns both, `PING`, `ECHO` and `HELLO` included, where the second element is always empty. What a client sees is not the whole of what a follower would need to know happened: a `GET` that finds an expired key has to produce a deletion nobody asked for, with no write command anywhere in the request to carry it. That case doesn't go through a handler's own effects list either -- the key expired inside `lookup()`, which `GET` only called, so the `DEL` goes onto the store's own pending queue instead, which `server.py` drains once per dispatched command, ahead of the handler's own effects in whatever a follower would apply. The active expiry sweep is the queue's second producer, draining it for itself once per tick rather than once per dispatched command, since it runs outside dispatch entirely. Both lists reach `server.py` and both are discarded there: nothing here consumes an effect, because replication is specified in full and deliberately unbuilt. The shape was built and exercised ahead of a reader that was never written, and it stays: producing the fact correctly is already done, rather than retrofitted onto handlers that never had to account for it, and the README lists the unread list among the four things in the code that are present and that nothing in a running server puts to use.

### Why the last `LPOP`/`RPOP` off a list emits no `DEL`

`Store.remove()` deliberately appends nothing to the effects queue, which is what keeps the empty-container cleanup from doubling the replication stream. A follower applies `LPOP`/`RPOP` through its own dispatcher, exactly as the leader did, so the same emptying pop triggers the same cleanup against the follower's own copy of the list -- a `DEL` sent alongside the pop would be redundant, not corrective. The pair is idempotent, which is exactly why nothing breaks today and why a redundant `DEL` would go unnoticed: it would simply double the replication traffic on every list that empties, with no test able to tell the difference from a stream a leader and follower already agree on.

### Why the write path exists before any reply is large

The write path is built with the first reply, before any reply is large: a reply can be as large as `ECHO`'s own argument without any command touching a keyspace, and a socket can already refuse to take a large write in one call. Measured against a copy of this server whose only write path was a bare `socket.send()` with nothing behind it to catch what the kernel wouldn't take: 200,000 pipelined `ECHO` commands down one connection, with the client writing every request before it read a byte, which is what fills the kernel's send buffer the way a client that has stopped draining does. This server's write path, with the pause described under backpressure below switched off (`--write-buffer-high-water 0`), delivers all 200,000 replies whole on every run; with the pause on, which is the default, this exact client does not complete, and that section says why. The bare-`send()` copy delivered between 80,000 and 115,000 of them, the count moving run to run on the same workload, and the shape of the loss matters more than the count: one reply -- the one being written when the buffer filled -- arrives cut in half, and almost every reply after it is never transmitted at all, because a `send()` against a full socket raises `BlockingIOError` and writes nothing, so the discarded remainder is a whole reply rather than the tail of one. A write path that survives a partial write isn't an optimization added later -- it's the difference between a reply and a reply the client never sees, and it belongs with the first reply rather than waiting for a request large enough to make the gap obvious.

### Why a protocol error carries the commands parsed ahead of it

`Connection.take_commands()` builds its return value -- a list of the commands parsed so far -- in a local variable, and a parser failure partway through a batch raises straight through that frame, discarding the local along with it. A client that sent two good commands and one malformed one in the same write would then see neither of the first two answered, only the error, even though both had already parsed cleanly. `BatchProtocolError` is `resp.ProtocolError` carrying one more thing: `commands`, the list `take_commands()` had already built before the raise. It has to ride on the exception, because the exception is the only thing that survives the frame it is raised from and already crosses the connection/server boundary every caller of `take_commands()` was already prepared to catch; a slot on `Connection` would have to be set before every raise and cleared before every successful return, on a connection that is about to be closed either way -- one more field to remember at the one place that already clears connection state on the way out.

It is a subclass rather than a new exception type so every existing catch of `resp.ProtocolError` -- including this module's own tests -- keeps catching it with no edit. `commands` is `[]` when nothing had parsed ahead of the failure, never a missing attribute, so a caller never has to ask whether the field is there before reading it. `server.py` dispatches that list, answering every command it holds, before it queues the error and closes the connection -- in that order -- so the reply a client sees matches what it would have seen had it sent the same commands as separate writes instead of one. An over-cap bulk length or multibulk count is one more way for a protocol error to land partway through a batch, and it fails there exactly where a malformed inline command does.

### Why the cap on a queued reply closes the connection

A client that keeps asking and stops reading is the cheapest way to spend this server's memory. Replies queue in a per-connection buffer, and the cost is not paid in the bytes it takes to ask: one 64 KiB write holds 1,820 `GET`s of a sixteen-byte key in the multibulk framing every client library sends, 936 of a fifty-byte key, 2,730 of a five-byte one and 3,276 of a one-byte one. The count is set by the key's length and the framing; the size of the value does not enter, and an inline command is shorter than its multibulk form and packs more. Every reply is buffered whole, and the value they all name was stored once. Measured with no limit set, 2,200 bytes of pipelined `GET` against a single 1 MiB key grew the process by tens of megabytes -- four orders of magnitude more than the request -- while the keyspace itself never grew at all. The exact figure is not worth quoting: it is resident-set size sampled from outside the process, and how much of a reply is held in the write buffer rather than absorbed by the kernel's own socket buffers varies with the platform and with the moment the sample lands. What does not vary is the shape, which is the whole reply set held at once. That is a different shape of problem from the `SET`-until-it-dies case described under Limits in the README, which costs a byte per byte.

`--write-buffer-limit` bounds it, and what it does when exceeded is a close. The obvious answer is backpressure: stop reading a connection whose replies are piling up, resume when they drain. On its own it deadlocks a client that writes every request before it reads a byte, and the code that implements it looks correct. That client -- the workload the write path section above is built around, and what a pipelining client library does -- fills the queue, has its own reads stopped, and then blocks in `send()` waiting for room that only its own reading would create. Both sides wait. Measured on macOS loopback against a build with a 1 MiB mark and no other change: 200,000 pipelined `ECHO`s, five megabytes of requests written before the first read, and the client's `sendall()` never returns. This server pauses reading anyway, at the high-water mark the next section describes, and that measurement is the price of doing so and not a hazard it avoided. Measured again against this server at its shipped defaults on macOS loopback, with an eight-byte argument on each `ECHO`: 150,000 of them (4.2 MB of requests) completed in four runs of four, and 200,000 (5.6 MB) did not complete in any of four. The sender stopped making progress between 4.1 and 5.5 MB, a point that moves from run to run, and in the run that checked, the server still held the connection and had logged no warning; with the mark at 0 the same 200,000 were sent and every reply read in four runs of four. `redis-py` 8.1.0's `pipeline(transaction=False)` is that client, since it packs the whole batch and sends it before it reads any reply: with the same `ECHO`, 20,000 of them completed at the shipped defaults, 200,000 did not complete within twenty-five seconds, and 200,000 completed with the mark at 0, in one run of each. The cost of the pause is therefore a client that hangs rather than one that is disconnected, and the limit still closes in the cases a pause cannot help: a reply larger than the limit, which no amount of not reading will make smaller, and the replies to one read's batch, which the pause cannot unqueue once they are parsed.

It is consulted twice, and both places are load-bearing. After a flush, because what a limit should measure is what the kernel would not take rather than what was queued a moment ago -- a reply larger than the limit that leaves in one `send()` costs nothing to hold. And inside the dispatch loop, because one `recv()` can carry thousands of commands and queueing every reply before the first send is exactly how a few kilobytes of request commit gigabytes: checked only after the batch, a 4 MiB limit was measured letting 104,597,124 bytes accumulate first. The in-loop check flushes before it judges, so a client whose replies the kernel keeps taking is never closed however deep its pipeline gets, and the peak is bounded to the limit plus one reply. That includes the refusals a rate limit answers with: the refusal path queues its error and then reaches the same check, and under a flood of refusals the peak measured 111 bytes against a 100-byte limit. What it does not do is wait: this is a hard limit in the reference's sense, and a hard limit closes a connection for holding too much, not for failing to read. A client that reads continuously but slower than the server produces is closed the same as one that stopped: `redis-cli --pipe`, which reads concurrently by design, is disconnected here at `--write-buffer-limit 4096` by a hundred pipelined `GET`s of a single 50 KB value. What trips the limit is the pipelining and not the reading: at that limit `redis-cli --pipe` was closed in 10 of 10 runs of the hundred pipelined `GET`s and in at least 9 of 10 runs, in each of two sets, of a hundred alternating `SET`/`GET` pairs at the same value size, because it writes without waiting for replies however concurrently it reads. A lock-step client, which sends one command and reads its whole reply before sending the next, drains between commands and is not closed: 100 of 100 runs of alternating pairs completed. redis-server 7.2.7 configured with `client-output-buffer-limit normal 4096 0 0` disconnects both `redis-cli --pipe` shapes too, 10 of 10 runs each, and for the pipelined `GET`s its log says it overcame its output buffer limits. The reference pairs its hard limit with a soft one -- a lower ceiling that has to be held for some number of seconds before it counts -- which is what makes a merely slow reader survivable there. That is the half not built here. At the shipped defaults what keeps a slow reader from reaching the hard limit is the pause in the next section -- which holds it to the mark plus the one batch that crossed the mark, and that is not near the mark: measured, a paused connection holds almost the whole of the 32 MiB ceiling rather than anything near the 1 MiB mark, and the README carries the figure and the aggregate it implies, so the pause is what keeps the limit from firing and not what keeps the queue small; with the limit configured below the high-water mark, as in the example above, the limit is the only control and closes the reader the way the reference's does.

### Why a connection owed more than a mark stops being read

A limit that only closes treats a client that is slow the same as one that has stopped, and lets either hold the limit's whole worth of memory before anything is done about it. `--write-buffer-high-water` and `--write-buffer-low-water` add a stage ahead of the close: a connection with more than the high-water mark queued for it stops being read, and is read again once the queue has fallen to the low-water mark. Reading is what creates replies, so a connection that is not read cannot add to its own queue, and one that reads slowly is held to the pace it drains at instead of being closed for the depth of its pipeline. Both interests are decided in `_flush`, the same place write interest is decided, so there is one source of truth for what a connection is registered for, and read is decided first. The order matters: a paused connection whose buffer has just emptied wants neither reads nor writes, which is an empty mask, and the selector cannot hold one -- on the kqueue backend macOS and the BSDs use, `modify()` with an empty mask raises `ValueError` and drops the registration on its way out, where epoll accepts it -- so the loop spells an empty mask unregistered and never asks for one. Deciding read first means a buffer that drained to empty has already passed through the resume, so the write decision never meets a connection that wants neither. The pause starts above the high-water mark and the resume at or below the low-water mark, so a queue exactly on the high-water mark is not paused and one exactly on the low-water mark is resumed. Between the marks nothing changes, which is the hysteresis and the reason there are two: equal marks would pause and resume a connection on every event, so a low-water mark that is not below the high-water one is refused at the CLI and by the constructor. A high-water mark of 0 is the exception, because it disables the pause and leaves the low-water mark with nothing to be inconsistent with. With the pause off, reading goes on however much is queued, and that is the setting under which the write path section's client that writes everything first completes.

The mark is consulted inside the dispatch loop as well as after the batch, for the reason the limit is: a pause decided once per batch would let one `recv()` of pipelined `GET`s queue the whole batch before anything throttled. What it cannot do is unqueue what the batch has already parsed. Every command in a batch is still dispatched, so the mark bounds what a connection accumulates across reads and not what one read can add, and the limit stays as the ceiling on a batch: a flush inside the loop closes the connection once the queue is over the limit and the kernel will take no more, so the peak is the limit plus one reply, a refusal under `--rate-limit` being a reply and its path reaching the same check. While a connection is paused its requests wait unread in the kernel's receive queue and are answered in order after the resume; nothing is dropped or reordered, for as long as the server keeps running. A stop is the exception and it is a large one: the requests are waiting unread for however long the connection stays paused, which is until it disconnects, and none of them is dispatched, so a pipeline a paused client's `send()` has already returned for is lost in full. The drain discards them in two ways and not one. Those a pass of it reaches it reads and throws away; those it does not reach stay in the receive queue until its last look, which reads and throws them away too and counts them, so the close that follows finds the queue empty. Which way a given byte goes is not a property of the client but of how long the drain lasts, and the drain ends the moment no connection is owed a reply -- so a client that reads its replies ends it sooner than one that does not, and `--shutdown-drain-timeout 0` ends it before a single read pass. Losing the whole pipeline takes the pause to have fired, which takes more queued replies than the two kernels will hold, and how much that is moves from run to run; below that amount what is lost is whatever the loop had not read when the stop landed, rather than the whole pipeline -- measured with the pause unable to fire, at the default flags and with a client that never reads, a prompt stop discarded most of a pipeline and a server given three seconds to catch up discarded none of it, so what is lost there is a function of the settle and not a bound either way; `README.md` carries the ten runs, their range and their median. Measured at the shipped defaults over twenty-three runs, each preceded by twelve 1 MiB replies so that the pause fires: of 50,000 pipelined `SET`s whose bytes the kernels had accepted, every one was discarded and none executed, and in 12 further runs instrumented from inside the process the pause edge was seen in each. How many are executed is not fixed: it depends on whether the two kernels had absorbed enough of the twelve replies for one more read to land before the pause fired, and none was in these runs, though earlier probes of the same shape executed some, so read the loss as the whole pipeline and not as a figure near it. The process exits 0. A client's end of input is clean when everything it sent had reached the server's receive queue by that last look, because the drain reads and discards the receive queue of every connection it was serving and not only the ones a pass of it read; a client swept from the accept backlog is not served, and its queue is counted and left, so it sees the reset, as the shutdown section says. `README.md` carries the runs. The drain reports the bytes it discarded in both ways on its one line -- the whole of what this probe's client sent. With the pause off (`--write-buffer-high-water 0`) the figure depends on the settle: given three seconds for the server to catch up, every request executed and the figure was 0, and with a prompt stop it was above 0 in every run, with some requests executed and the rest discarded. `README.md` carries the byte figures and the run counts of the pause-off runs and of the earlier probes. Turning the pause off removes the loss's certainty, not the loss. The drain's line is the only place the loss is reported at all, and the shutdown section above says why the figure does not move the line's level. A paused connection is still a connection: it is reaped when its peer goes away, and the others are served meanwhile.

The pause has three costs, and all three are accepted. The first is the hang described under the cap above: a client that writes everything before it reads anything hangs rather than being disconnected, because its writes stall against a server that has stopped reading it. The second is that nothing closes a client that stops reading and stays connected. The pause is what keeps `--write-buffer-limit` from firing for it, not what keeps its queue small or anywhere near the high-water mark, as the previous section measures; `--incomplete-command-timeout` is suspended for every paused connection, as the next section describes, so it does not bound it whether or not it holds a half-sent command; and it holds the mark's worth plus the one batch that crossed it until it disconnects. That is bounded, per connection by the mark plus that batch, which the limit caps while it is on, and over all connections by `--max-connections`, and it differs from the reference, which keeps reading such a client and closes it at the hard limit configured for ordinary clients, if there is one. It is not fixed, because a bound on how long a connection may stay paused would be a control of its own, and `--incomplete-command-timeout` is not that control: it bounds a half-sent command and is suspended for a connection while it is paused. The third is the one measured above: a paused client's requests wait unread for as long as it stays paused, and a stop discards every one of them, so a pipeline its `send()` has already returned for is lost in full. That one is reported, on the drain's own line. `--write-buffer-high-water 0` removes the pause's share of it -- the whole pipeline, lost with certainty -- and not the loss itself: a stop still discards whatever the loop had not read, which the paragraphs above measure at anything from none, given time to catch up, to most of the pipeline, with a prompt stop. The shutdown drain does not decide read interest: `_flush` leaves it alone while the drain runs, and the drain itself switches reading back on for a connection that owes bytes, as the shutdown section describes. A client that only falls behind is what the pause is for and not a case it fails: once it is more than the high-water mark behind it is paused, and it is read again as it catches up to the low-water mark.

### Why the incomplete-command deadline is suspended while a connection is paused

`--incomplete-command-timeout` closes a connection that has held a command it has only partly sent for longer than the limit, and the clock it runs on is a slot on the connection, `incomplete_since`, that the server arms when the connection begins holding a command and clears when it holds none. It is armed once and not restarted by later bytes, because a client sending one byte a second is the client the flag is for. It is armed again only when a batch completed at least one command and a tail is still held, since that tail is a different command; without that, a pipeline that every read cuts in the middle of a command would never present a clean buffer and would be closed at the timeout however quickly each command completed. A paused connection is the case that needs more. The server is what stopped reading it, so it cannot finish its command, and a deadline that kept running would close a client for the server's own decision. Two simpler designs fail. Skipping paused connections in the sweep while leaving the arm time alone closes the client the instant reading resumes, having given it no chance to send the rest. Leaving the deadline running closes it while it is paused. So the deadline is suspended rather than skipped: pausing clears `incomplete_since`, and resuming arms it afresh from that moment if a command is outstanding, so a client is owed a full timeout from the moment the server starts reading it again.

Both edges are edges and not levels. The flush that decides read interest runs after every dispatch, including one that completed no command, so a re-arm keyed on the connection being below the low-water mark would restart the deadline on every byte of a trickle and reproduce the defect the one-shot arm exists to prevent. `set_read_interest` reports whether the registration changed, which turns the level into an edge without asking the selector anything: only the flush that did the pausing clears the deadline, and only the one that did the resuming, for a connection that holds a command, arms it. The two writers are then disjoint, because `_flush` writes the slot only on a pause or resume edge and the read path writes it only after parsing, and a paused connection receives no read events that could overwrite a suspension. The order inside the read path matters: it arms before it dispatches the batch, because dispatching can pause the connection and the pause's clear must be the last write. Arming after the dispatch would read the cleared slot as empty and start a deadline on a connection the server had just stopped reading. The re-arm on resume looks like it leaves a cost, and it does not. A reader that oscillates across the marks would restart its deadline at every resume, but a connection holding a half-sent command cannot oscillate: crossing the high-water mark needs new replies, new replies need a command to complete, and the half-sent command sits at the front of the read buffer and blocks the parse of everything behind it. So while one is held the queue only falls and the marks are crossed at most once. Measured at both low-water settings, with twelve further commands sent behind the half-sent one: one resume, the queue never rose, no reply was produced behind the held command, and the connection was closed 3.06 seconds after that one resume armed the deadline against a three-second timeout. A half-sent command's life is therefore the time its connection spends paused plus one timeout, and the only unbounded term in that is the pause, which is the residual the previous section states. The sweep runs on the tick over a copy of the connection set, because closing discards from it, and closes through `_abandon`, so one close that fails does not end the sweep with every connection behind it still holding its half command.

### Why the inbound caps fire at the header rather than after the body

`resp.py` turns a bulk element's declared length into `body_end`, and `connection.py` then stores that as `_parse_needed` -- the buffer-growth commitment a connection makes to hold a body that has not arrived yet. A check placed after that computation has already made the commitment it exists to refuse: measured on this tree, a declared length of 65 MiB (`*3\r\n$3\r\nSET\r\n$1\r\nk\r\n$68157440\r\n`) sets `_parse_needed` to 68157453 before anything asks whether that length is reasonable. `--max-value-size` fires between the declared length being read and `body_end` being computed instead, so a refusal never buys the buffer it is refusing; `_parse_needed` still reading `0` after the refusal is what proves the check ran early enough, and it costs nothing to assert.

The multibulk count needs a cap of its own for a different reason than a bulk length does. `connection.py` builds a multibulk's argument list one element at a time, appending each element's bytes as they are parsed rather than reserving space for the declared count up front, so a large declared count costs nothing by itself until real elements actually arrive. What an uncapped count costs instead is that list itself: it is the one per-connection structure whose growth nothing else in this server bounds, and `--max-multibulk` puts a ceiling on how many elements one command may accumulate there.

The count is checked twice, not once, and the two checks stay apart on purpose. The first, against `MAX_MULTIBULK_COUNT`, is the reference's own unconditional ceiling and runs regardless of any flag. The second, against `--max-multibulk`, only runs when the flag is set -- `0` disables it, the same as the other two caps. Folding the pair into one comparison, `min(MAX_MULTIBULK_COUNT, max_multibulk)` say, would tie the first check to the same on/off switch as the second: `--max-multibulk 0`, meant to turn off only the configurable cap, would silently turn off the reference's own hard ceiling as well, at the exact moment nothing else is left standing in front of a runaway multibulk count. Two separate checks are what let `--max-multibulk 0` disable one without disabling both.

Both caps compare with `>`, never `>=` -- a length or count exactly at the configured value is accepted, matching both real Redis's own boundary and this server's existing convention for `--write-buffer-limit`. And the two bound nothing jointly: `--max-value-size` bounds one inbound element and `--max-multibulk` bounds one command's element count, so a client can stay under both and still send enough pipelined commands against one large key to queue far more than either names, because neither multiplies by how many times it is asked. What bounds that is `--write-buffer-limit`, one connection's queued output, which holds a connection to the limit plus one reply while it is on; with the limit at `0` nothing does. `--incomplete-command-timeout` is a control of another kind: it bounds how long a command may stay half-sent, not how many bytes any of the caps above can hold.

### Why the connection cap refuses at accept rather than reserving a slot

`--max-connections` is checked in the accept callback, after `accept()` has returned a socket and before anything owns it: if the connection set already holds COUNT connections, the socket is closed on the spot with nothing written and the callback returns. A refused connection is never registered with the selector, never given a `Connection`, never added to the set, and so never counted by `INFO`'s `connected_clients`. The count is the set's own length, because a second counter would be a second copy of a fact the set already holds and would disagree with it silently, in both directions, the first time a path changed one and not the other.

The refusal is a close and not an error reply because a reply would be a `send()` from inside the accept callback, on a socket nothing tracks, on the one thread this server has, for a client that by construction is not being kept. A send that cannot complete has nowhere to wait: the choices are to block the loop on a peer that is over the limit by definition, or to track a connection in order to refuse it. A close is a refusal the client can see, and what it cannot see is why, so the server says so on its own side. The first refusal of an episode is logged as a warning naming the limit, the rest are logged at debug level, and one short line with no address is written once per `REFUSALS_PER_LINE` refusals, so a run that never ends still leaves a trace. The volume has to be bounded at all because a client retrying in a loop is refused as fast as it can connect, and logging writes to a standard error whose write blocks the only thread there is; that is the reasoning that bounds what a failing periodic task reports, with a larger count here because a periodic task fails at most once an interval and a retrier does not wait for one. A new episode begins only after `REFUSAL_EPISODE_GAP_SECONDS` with no refusal at all, and a close does not begin one. Re-arming the warning on a close looks natural and is wrong: a freed slot is what a retrying client is waiting for, so with a saturated cap whose slots turn over a close comes between every pair of refusals, and every refusal would warn, which is the opposite of what the rule is for.

The alternative was to accept the connection into a boundary slot, a state in which it is registered and tracked but not yet a client, and decide there: admit it, or refuse it with a reply and a graceful close. That shape earns its keep in a server with more than one reason to hold a connection it has not decided about. This server has one such reason, the cap. A second would be replication's, a follower link held on a deadline of its own while it is set up, and replication is not built here, so the structure would have been carried for nothing: a state every connection passes through, a path in the close code every other connection shares, and a second place that has to agree with the count. The flat check does the one job it has and keeps no state of its own. If a second reason to hold a connection undecided ever arrives, the place to put it is known and nothing here stands in its way.

The comparison is `>=` where every byte limit in this server is `>`, and the two are the same rule applied to different questions. A byte limit compares a quantity the connection already holds against a ceiling it may legally reach exactly, so a length equal to the limit is accepted. The cap asks whether there is room for one more, so a count equal to the cap is full: `--max-connections 2` admits two clients and refuses the third, where reading it the way the byte limits are read would admit three. It looks like an off-by-one until the question is stated. The default is 1024, well clear of 50, because `redis-benchmark -c 50` is the standard invocation and a cap under it refuses some of the benchmark's own clients and turns it into a test of the cap; a cap of exactly 50 is enough, since it admits exactly 50, and the flag itself takes any non-negative value. `0` means no limit and nothing is refused, as it does for every limit flag, which is the reading `--shutdown-drain-timeout 0` inverts, as the shutdown section above says. The cap bounds how many clients there are and not what any of them can hold: each limit above is still per element, per command or per connection, so none of them becomes a bound on memory because there are at most COUNT connections to apply it to.

### Why the rate limit is counted per command, on a monotonic clock, and answered without a close

`--rate-limit` is consulted inside the loop that dispatches a batch, before each command, and not once per readable event. One `recv()` carries a batch, and a pipelining client puts thousands of commands in it, so a check made once per event would charge all of them one unit and the limiter would bound how often the socket was read rather than how many requests were made. That is the placement `--write-buffer-limit` has, checked inside the loop as well as after the flush, and the reason is the same. `README.md` carries the run that shows it: a pipelined batch of `PING`s written in one `sendall` to a real `server.py`, answered in full with no flag and cut to the limit with one.

The window is a deque of `time.monotonic()` readings and not of wall-clock ones, because what it measures is a duration. A wall-clock window breaks under an NTP correction, and in the direction that permits a flood: a clock stepped forward puts every reading in the window outside it at once, and the limiter forgets the burst it was holding. This is the opposite case from the expiry deadlines, which are wall-clock because `PEXPIREAT` is Unix milliseconds by protocol and a deadline has to be a timestamp two machines read the same way; the section above on deadlines and durations has that argument, and this is a duration.

A check pops readings from the left while the oldest is at or before now minus the window, refuses if as many as the limit remain, and otherwise appends the new reading and permits. Each reading is appended once and popped once, so a check is O(1) amortised, which matters on one thread because an expensive check does not slow one client down, it slows every client down. The readings are popped and not merely ignored, and that is the whole reason for the shape: a version that counted the readings still inside the window would answer every question correctly and keep one reading per request for the life of the connection, a leak that behaves. A refusal records nothing, so the deque holds permits only and never more than the limit, and `len()` of the window, how many permits are inside it, is what a test asserts is bounded. The comparison with the window's edge is `<=`, so a reading exactly one window old has left it, the way an expiry deadline equal to now is already expired, and the comparison with the limit is `>=` for the reason the connection cap's is: the question is whether there is room for one more.

An over-limit command is answered `-ERR rate limit exceeded` and not dispatched, for that command alone, and the connection stays open and is still read, so the next command is judged on its own, for as long as the refusals do not themselves pass `--write-buffer-limit`: a refusal is a reply like any other and that limit applies to it, so ten refusals under a small configured limit closed the connection. The reply names no figure, because the limit is the operator's configuration and not the client's business. A close would be the wrong answer twice over. To the client it is indistinguishable from the close a protocol error gets, so being limited and having sent a malformed command would look the same, and the reconnect that followed would arrive with a fresh budget, so the limit would be undone by the way it was enforced.

The budget belongs to the connection and not to the address it came from, so a client can start again with a full one by reconnecting. That is a cost and it is accepted. Counting per address needs a table shared between connections, and this loop has none; counting per connection is the cheap correct thing. `--max-connections` is not a mitigation: it bounds how many connections, and so how many budgets, exist at once, and not how often a client may open a new one, and `README.md` carries the measurement of how far that goes. The window lives in `rate_limit_state` on the connection it counts and is built on a `client` connection's first command under a limit and not at accept, so a connection that sends nothing, an exempt one and a server with no limit never allocate one: with `--rate-limit 0` the check is a method call that tests one attribute and returns, and `README.md` carries what it costs.

The check skips any connection whose role is not `client`, and it is a test for `client` and not `is not Role.FOLLOWER`, because the three roles do not sort into two. A follower is a peer syncing off this process; `leader_link` is this process's own outbound connection to its leader. A two-value check classifies that link as an ordinary client and rate-limits the process's own replication stream, with no error anywhere saying so. The check therefore names `Role.CLIENT` and nothing else, and it is the tests that name both of the others, building a connection with each role and asserting that neither is limited, since a check written against `follower` alone would pass one and fail the other. Nothing in a running server sets either role, as every accepted connection is built a `client` and the flag that would start a server as a follower was never written, so the exemption is code that runs on every command with nothing to apply to: the first of the four things `README.md` lists as present and unused by a running server, and reached only by tests that build a connection with each role by hand.

`--rate-limit 0` turns the limiter off, as `0` removes the limit on `--write-buffer-limit`, `--max-value-size`, `--max-multibulk`, `--max-connections` and `--incomplete-command-timeout`, and `--rate-limit-window` takes no `0` at all. Every other numeric flag has some reading of `0`: off, no drain, resume only when the queue is empty, a port the kernel chooses. A window has none, because 100 requests per 0 seconds puts every reading outside the window the moment it is taken, so the limiter would permit everything and say nothing, and an operator who typed `0` meaning off would have a limiter configured that never fires. So `0` is refused with a message that names `--rate-limit 0` as what turns the limiter off, and a negative window is refused with the same one. A negative `--rate-limit` is refused too, both flags at both doors, the CLI and `Server.__init__`, and the window takes the same `2**63 - 1` ceiling as every other duration. The window is whole seconds.

### Why write interest turns off the moment the buffer empties

`event_loop.py` asks the selector whether a connection is writable only while that connection's write buffer is non-empty, and clears the request the instant a flush empties it. An idle, healthy socket is writable on nearly every pass, so a write request left registered against an empty buffer would have the selector reporting that connection ready again and again with nothing queued to send -- the loop would spend its time asking the kernel about a socket that has nothing to say. The selector's own mask is also the only place this fact is kept: a separate flag on `Connection` would be a second copy that can disagree with the selector, in either direction, with nothing around to notice when it does.

### Why an unknown command gets an error, not silence

`-ERR unknown command '<name>'` costs one write and leaves the connection open. Silence costs nothing to produce and is worse to receive: a client that gets nothing back cannot tell a slow server from one that will never answer, and has no way to distinguish "still working on it" from "doesn't understand this at all" -- it can only wait, or guess. An error reply lets a client's own retry and timeout logic run the way it was built to, on a connection that never had to be dropped over a single bad request.

### Why one exception boundary covers a whole connection

Every step of handling a connection's traffic -- reading, parsing, dispatching, writing -- runs inside the same `try`/`except` in `server.py`, reached from both the readable and the writable callback, rather than one boundary per callback. Two boundaries are two places to write a slightly different close path, and the failure that produces is invisible until a client happens to hit the one that's wrong: a bug that closes its connection cleanly when it surfaces on a read, and takes the whole process down when the same bug surfaces on a write. A single-threaded server has exactly one thread to lose, which is what makes this boundary mandatory rather than a defensive habit -- every other connection's traffic stops the moment an unhandled exception reaches the top of that thread. The boundary's own recovery is the second half of that: closing a connection can itself fail -- the flush, the deregistration and the socket close can each raise -- and a raise from inside the handler reaches the top of the thread just as surely as the original one would have. One `_abandon` answers for that, reached from the boundary, from the incomplete-command sweep, and from both sweeps the shutdown makes over the connection set, the drain's opening walk and the teardown, alike, so there is one place that decides how a connection which cannot be closed is disposed of rather than one per caller.

### Deliberate differences from real Redis

- An unknown command answers `ERR unknown command '<name>'`. Real Redis appends the first few arguments it received to that message; this server never does, and the argument list plays no part in it. That does not make this server's message the shorter of the two, which is the easy thing to assume: real Redis renders the name through a `%.128s` conversion and its whole reply tops out at 181 bytes however long the name was, while this server echoes the name whole, bounded only by `--max-value-size` — a command name is a bulk element like any other, so the same cap that refuses an oversized value refuses an oversized name. A 200,000-byte command name answers 181 bytes there and 200,025 bytes here, comfortably under the 64 MiB default. It is the largest reply this server can be made to produce with no keyspace to put anything in, up to that cap, rather than at a size nothing bounds.
- `HELLO` with an argument other than `2` answers `NOPROTO unsupported protocol version`, whatever that argument is. Real Redis has two rules here that this server collapses into one: a non-numeric argument gets a different error naming a parse failure specifically, and `3` isn't an error there at all -- it's RESP3, a second protocol version a real server accepts, switching that connection to a different reply grammar. This server speaks RESP2 and nothing else, so `HELLO 3` is refused with the same message as `HELLO banana`, and there is one rule to remember rather than one rule plus two exceptions.
- `HELLO` takes the protocol version and nothing else. Real Redis also accepts `AUTH <username> <password>` and `SETNAME <name>` after it, so `HELLO 2 AUTH u p` answers `WRONGPASS` there and `ERR wrong number of arguments for 'hello' command` here. Neither option has anything to act on -- there is no authentication in this server, and no connection name to set -- and a client library that opens with `HELLO 2 AUTH ...` gets an arity error rather than an authentication one.
- `HELLO` counts its arguments before it looks at any of them. `HELLO x y` answers `ERR wrong number of arguments for 'hello' command` here and `ERR Protocol version is not an integer or out of range` there; `HELLO 2 BADOPT` answers that same arity error here and `ERR Syntax error in HELLO option 'BADOPT'` there. Real Redis parses the version first and then walks the options, so it names whichever one is actually wrong; this server takes a version and nothing after it, which makes every one of those shapes a wrong argument count before it is anything else. The more specific complaint is the one that never gets made.
- A negative multibulk count is a protocol error. `*-1\r\n` gets `ERR Protocol error: invalid multibulk length` here and the connection closes; real Redis consumes any count of zero or less without replying and goes straight on to the next command in the same buffer. A negative *bulk* length inside a multibulk -- `$-1` -- is rejected by both, which is what makes this one easy to miss.
- A bulk body must be followed by `\r\n`. `*1\r\n$4\r\nPINGXX\r\n` declares four bytes and then supplies six, which this server refuses with `ERR Protocol error: unterminated bulk string`; real Redis advances past the body by its declared length and never inspects the two bytes after it, so it answers `PONG` and treats the stray bytes as an empty inline command. That error string has no real-Redis equivalent -- this server is the stricter of the two here.
- Every `\r` that ends a header must be followed by `\n`. Real Redis finds the `\r` and steps two bytes past it without ever looking at what the second byte is, so `*1\rX$1\r\na\r\n` and `*1\r\n$1\rXa\r\n` both parse there and answer `ERR unknown command 'a'`; this server refuses them with `invalid multibulk length` and `invalid bulk length` and closes. The same reading is what makes the entry above refuse `*1\r\n$1\r\na\rX`. Three positions, one rule: a lone `\r` is a terminator there and a framing error here, and this server is again the stricter of the two.
- A NUL byte ends an inline command line. `PING\x00X\r\n` runs `PING` here and everything after the NUL is dropped, which is what real Redis's own argument splitter would do with that line -- but real Redis never gets there, because it locates an inline command's end with a C string scan that stops at the NUL, so the line never looks complete and that connection stops answering permanently. The difference is invisible to any client that does not send a NUL.
- A NUL byte inside a *multibulk* command name is part of the name. `*1\r\n$4\r\nPI\x00G\r\n` answers `ERR unknown command 'PI\x00G'` here, the NUL sitting raw in the error body; real Redis builds the same message with a C string conversion that stops at the NUL, so it reports the command as `PI` and never sees the rest of it. Both servers answer and both keep the connection open, so the difference is only in what the message says was asked for.
- A NUL anywhere in multibulk *framing* is a protocol error here and silence there. `*1\r\n\x00\r\n`, `*\x001\r\n` and `*1\r\n$\x004\r\n` each get an error and an immediate close from this server -- `expected '$', got '\x00'`, `invalid multibulk length` and `invalid bulk length` respectively. Real Redis answers none of the three: it stops answering on that connection permanently, so a client sits waiting on a reply that will never come instead of reading an error and reconnecting. This is the same reasoning as the unknown-command entry above, applied to a connection that has to be dropped: something that says why beats nothing at all.
- A declared *bulk* length over `--max-value-size` is refused at the header, before a body byte of it is read: `*1\r\n$68157440\r\n` (65 MiB, no body sent) answers `ERR Protocol error: invalid bulk length` and closes, the same string real Redis answers for the same shape. The default is 64 MiB; real Redis's own `proto-max-bulk-len` defaults to 512 MiB. The boundary is `>` on both servers -- a length exactly at the cap is accepted, one byte over is refused -- and the cap applies to every bulk element, the command name and any key included, because the check sits at the framing layer before an element has a role.
- A declared *multibulk* count over `--max-multibulk` is refused the same way: `*1048577\r\n` answers `ERR Protocol error: invalid multibulk length` and closes. This is a divergence rather than a port -- real Redis refuses nothing below its own `INT_MAX` ceiling and waits patiently on `*1000000000`, because it does not reserve space for the declared count up front: `networking.c:2301` caps the reservation at `min(count, 1024)` argument pointers and `:2381` doubles from there as elements arrive, so a declared count of a billion commits 8 KiB and not eight gigabytes. It is a small commitment rather than none. The default, 1,048,576, bounds how many elements one command may accumulate in that list before this server answers it; no client in this project's test set comes near that many.
- A **terminated** inline line over `MAX_INLINE_SIZE` is refused with `ERR Protocol error: too big inline request`, the reference's own string. The ceiling is a constant, 64 KiB, rather than a flag -- an inline command's own length has no flag table entry to live in. It bounds the inline path alone: a multibulk `ECHO` quotes back an argument up to `--max-value-size`, far past this ceiling, so what bounds the largest reply this server can be made to produce with nothing in the keyspace is that flag rather than this constant. Real Redis's own refusal is a band here, not a boundary: its check only runs on a read that has not yet found a newline, and it reads in 16 KiB quanta, so where a terminated line lands depends on how the kernel happened to split it -- measured at twenty repeats per size, every line up to 80,896 bytes was answered in full every time, every line from 98,303 bytes up was refused every time, and sizes in between gave both answers across repeats. No single number describes where the reference gives up, so none is written here as if there were one.
- A line is never refused for running on without a newline, in any of the three places one can: real Redis gives up at 64 KiB on an inline command with `ERR Protocol error: too big inline request`, on a multibulk count with `ERR Protocol error: too big mbulk count string`, and on a bulk length with `ERR Protocol error: too big bulk count string`, and this server keeps buffering in all three. These are not rules about unterminated lines specifically -- as the entry above shows for the inline case, real Redis applies each of its three ceilings to a line that has ended too. What this server still leaves open is narrower than the entry above closes: a line with no terminator yet has no declared length to compare against anything, so it is not bounded in size at all. `--incomplete-command-timeout` bounds it in time, closing a connection that has held an unterminated line for longer than the limit, which leaves a client free to grow its buffer by however much it sends before then.
- A bulk element's type byte is checked before its header line is complete. `*1\r\nX` answers `ERR Protocol error: expected '$', got 'X'` here the moment the `X` arrives; real Redis searches for the terminator first and says nothing until the line ends, then answers the same error. Byte zero cannot retroactively become `$`, so the verdict is identical either way and only its timing differs -- but it differs on the wire, and refusing a malformed byte the moment it arrives rather than waiting it out is the rule this server follows elsewhere.
- `EXPIRE`, `PEXPIRE` and `PEXPIREAT` register with arity exactly `3`. Real Redis 7 takes `-3` for this family, because it accepts `NX`, `XX`, `GT` and `LT` after the key and the time; this server accepts none of those four, so there is no minimum to leave room for -- `EXPIRE k 10 NX` answers `ERR wrong number of arguments for 'expire' command` here, where a real server would parse the option by name and act on it or refuse it. The exact arity says plainly what accepting no options would otherwise leave a reader to infer.
- `DBSIZE` and `INFO`'s keyspace count filter logically-expired keys. The reference filters in `KEYS` and not in the other two: with two logically-expired keys resident and the active expiry cycle disabled -- which needs `--enable-debug-command local`, since `DEBUG SET-ACTIVE-EXPIRE` is refused without it -- `DBSIZE` answers `3`, `INFO keyspace` answers `db0:keys=3,expires=2,avg_ttl=0`, and `KEYS *` returns only the one live key. The keyspace line here carries the first two of those three fields and not `avg_ttl`, which would be a statistic over deadlines nothing in this server computes. This server makes all three agree, because two introspection commands disagreeing about the same number is worse than either answer alone.
- `LPOP` and `RPOP` take a key and nothing else. The reference accepts an optional count -- `LPOP k 2` on a three-element list returns two elements and leaves one -- and the count changes the reply type from a bulk string to an array. Here it is a wrong-number-of-arguments error, matching this server's own precedent of exact arities over minimums that silently ignore a trailing option.
- `FLUSHALL` takes no arguments. The reference answers `+OK` to `FLUSHALL ASYNC` and `FLUSHALL SYNC` and `-ERR syntax error` to anything else. This loop is single-threaded, so the two options would name the same operation; `FLUSHALL ASYNC` here is a wrong-argument-count error.
- `CONFIG GET` answers from a table of the five parameters this server genuinely has -- `appendonly no`, `save`, `maxmemory 0`, `maxmemory-policy noeviction`, `databases 1` -- rather than from real configurability, which it does not offer. Every value is a true statement about this process: nothing is appended to a log, nothing evicts, nothing bounds the keyspace, there is one keyspace rather than sixteen, and `save` says when this server saves on a schedule. Three of the five equal the reference's own default because those defaults are "off" as well; `databases` does not, because 1 is the truth here and 16 is the truth there, and neither does `save`, which a default-configured reference answers with `3600 1 300 100 60 10000` -- a three-tier changes-based policy that a configuration with no save line at all gets as well. `save` is the one value read from the running server rather than fixed in the table: through the server slot of the connection asking, it reads the interval the save arm is scheduled at -- armed by `run()` before the listener opens and disarmed as `run()` returns -- so the reply agrees with the saves before a run, during it and after it, and it is spelt in the reference's own syntax. There each `<seconds> <changes>` rule fires once a whole-second clock is more than `<seconds>` past the last completed save and at least `<changes>` writes have landed, so this server's one rule -- a save every `--snapshot-interval` seconds, whether anything changed or not -- is `59 0` at the default 60 and `N-1 0` in general: measured on 7.2.7, `save "1 0"` saves every 2 seconds and `save "3 0"` every 4. A server with no save scheduled -- one under `--snapshot-interval 0`, one built with no snapshot path, or one whose save is not armed because `run()` has not started or has returned -- answers `""`, the reference's explicit spelling of snapshotting switched off, and so does a connection no server accepted. That spelling describes the schedule and not every write of the file: a stop signal saves whether or not a save is armed, as the shutdown section above explains. One spelling has no reference equivalent: at a one-second interval the rule is `0 0`, which 7.2.7's own parser refuses, since a rule's seconds must be at least 1, so no reference could ever report it. It is answered anyway, because `1 0` would claim a save every two seconds. The matching rules are the reference's, measured against 7.2.7 and identical on thirteen of the fifteen shapes tested: an argument with no glob metacharacter is looked up exactly, case-insensitively, and answered in the spelling the client used, so `CONFIG GET MAXMEMORY` answers `MAXMEMORY`; an argument with one is glob-matched over the table and answers canonical names; results are deduplicated across arguments, so `CONFIG GET * maxmemory` names `maxmemory` once; and an argument matching nothing answers the empty array rather than itself. What remains divergent is the size of the table, and one byte: a NUL. `configGetCommand` reaches the reference's matcher through `stringmatch`, which takes `strlen(pattern)`, so a pattern there stops at its first NUL -- `CONFIG GET "max*\x00"` answers exactly what `CONFIG GET "max*"` answers. This server carries the RESP length through and treats the NUL as a byte no parameter name contains, so the same pattern answers nothing. That is the reading every other NUL entry on this list already takes: binary-safe here, C string there, and this server the stricter of the two. Otherwise `CONFIG GET maxmemory*` names two parameters here and five there because the table is smaller, which is the whole of the difference -- all 65,536 single-byte class ranges were compared against 7.2.7 and the only disagreements left involve that NUL. Only `GET` is implemented: `CONFIG SET`, `RESETSTAT`, `REWRITE`, `HELP` and any unrecognised subcommand all answer `ERR syntax error`, where the reference answers `+OK` to the first two and names the subcommand it did not recognise in the last.
- `INFO` reports a fixed, small field set -- `redis_version`, `connected_clients`, `used_memory`, `role`, and the keyspace line -- and no persistence fields by choice: what a save is doing is a property of the process rather than of the keyspace a client reads, and the reference's persistence section reports mostly on a background save this server has no equivalent of, since the save here runs on the one thread everything else runs on. Uptime is absent deliberately too: it would be the first duration measured in the command layer, and every deadline in this server is absolute wall-clock time. The three whole-report selectors are accepted and all three select the same thing: on the reference `all` and `everything` widen the report past its default sections while `default` names the bare form's own set, and here every section is a default section, so `INFO all` and `INFO default` return the identical five fields a bare `INFO` returns. They are accepted rather than treated as unrecognised section names because an unrecognised name contributes nothing, and answering a client that spelled the bare form out with a zero-byte body is the one shape of "less" that tells it nothing at all.
- `redis_version` reports this project's own version, `0.1.0`, not the reference's. The field name is the reference's because tooling reads that key; the value is this server's because it is not `redis-server 7.2.7`, and saying so would make the one field a client trusts the one field that lies.
- A stop signal saves a snapshot even when periodic saving is off. With `--snapshot-interval 0` this server still writes the file at `--snapshot-path` as it exits cleanly, bar the one `--ignore-snapshot` pairing the shutdown section describes. A reference started with `--save ""`, its spelling of snapshotting off, writes nothing on `SIGTERM`: measured on 7.2.7, a server holding one key and started that way left its directory empty after the stop, and the control, started with a save point configured, left a `dump.rdb` there. The off switch does not mean the same thing in the two: there it disables every save, the one on the way out included, and here it disables the schedule only, because a save on the way out is not one. So `--snapshot-interval 0` is not a way to keep this server from writing its file, and `CONFIG GET save` answering `""` describes the schedule and not the stop.
- A stop signal waits for the replies already queued for clients. This server keeps sending them for up to `--shutdown-drain-timeout` seconds, reading and discarding what its clients send meanwhile and dispatching none of it, and then makes one last best-effort flush for each connection it closes before it exits. The reference does not wait: measured on 7.2.7, a client that had sent a run of requests for a large value and read none of the replies, so that a great deal was queued for it, saw the process exit at once, received only what the kernel already held for it, and then end of input. The wait is deliberate, because a reply already computed is not thrown away by a stop; the cost is that a client that never reads holds the exit to the whole timeout, which `--shutdown-drain-timeout 0` gives up.
- A connection over `--max-connections` is closed with nothing written. The reference answers one over `--maxclients` with `-ERR max number of clients reached` and then closes it: measured on 7.2.7 with `--maxclients 2`, a third client's first read returned that line and its next read returned end of input, where the same client here reads end of input at once. The silence is deliberate and the cap's section explains it -- a reply would be a `send()` from the accept callback, on a socket nothing tracks, on the one thread there is -- and the cost falls on the client, which can see that it was refused and not why; the reason is on the server's own log.
- An ordinary client's output buffer is limited by default. `--write-buffer-limit` defaults to 32 MiB where the reference leaves an ordinary client unlimited (`normal 0 0 0`, read back with `CONFIG GET` on 7.2.7), and `--write-buffer-limit 0` is the reference's behaviour. The cost is that a value between the limit and `--max-value-size` can be stored and then not read back, which the reference does too once a hard limit is configured; the cap's section has the measurement.
- A client that stops reading is paused, not closed. The reference keeps reading such a client and closes it at the hard limit configured for ordinary clients, if there is one; this server stops reading it at `--write-buffer-high-water`, so the limit never fires for it, and holds the mark's worth of replies plus the batch that crossed it until the client disconnects, bounded per connection and by `--max-connections` over all of them. A client that writes every request before reading any reply is paused the same way and hangs. `--write-buffer-high-water 0` switches the pause off. The backpressure section has the reasoning.
- A command that takes longer than `--incomplete-command-timeout` to arrive is closed, however steadily its bytes come. The clock starts when the command begins and later bytes do not restart it, because a client sending one byte a second is the client the flag is for, and the price is a command that is honestly slow, a large value over a slow link, which is closed without a reply and logged as a warning. The reference has no such deadline: measured on 7.2.7, a `PING` held half-sent for eight seconds was answered when the rest arrived, its `timeout` directive, which closes idle clients, reads `0`, and the only bound on a half-sent command is `client-query-buffer-limit`, 1 GiB. The default here is 30 seconds and `0` removes the check; a connection holding nothing is never closed however long it idles, and the deadline is suspended while the connection is paused and starts afresh when reading resumes.
