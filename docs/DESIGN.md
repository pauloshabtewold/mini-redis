# Design notes

Why mini-redis is built the way it is, and where it deliberately differs from real
Redis. Split out of the README so that file stays short; nothing here is required to
run or read the code.

### Why the protocol layer works in bytes

A parser built on `str` has to guess an encoding the moment it reads off the socket, and a value that isn't in that encoding comes out corrupted on the other side. `resp.py` never makes that guess: every value in this project -- keys, values, command names, error bodies -- is `bytes`, starting from the first line of the parser and continuing through the store and the snapshot format.

### Why a bulk string's body is delimited by its declared length

A bulk string is binary-safe, which means its body is allowed to contain the exact byte pair, `\r\n`, that ends every header line in the protocol. A parser that finds the end of a body by searching for `\r\n` truncates a body that happens to contain that pair and leaves the rest of it to be re-parsed as a bogus follow-on command. `resp.py` avoids the search: a body is read as a slice at a computed offset, `buf[start:start+length]`, and the only check left is that the two bytes right after it are `\r\n`. Header lines (`*N\r\n`, `$N\r\n`) are the opposite case -- their own length isn't declared anywhere, so searching for `\r\n` is exactly the right tool for them, and only for them.

### Why a header search carries a resume position

A bulk element reports the buffer length at which another attempt can make progress, because its body's length is declared in its own header and the parser can skip straight past it. A header line has no such number: `*N\r\n` and `$N\r\n` declare their contents but not their own extent, so nothing about a partial one says when its terminator will arrive. That leaves the terminator search itself, and a search that starts at byte zero every time a caller retries is quadratic in what one connection has sent -- 64 MiB arriving in 64 KiB pieces walks about 34 GB, which is the triangular sum of 1,024 reads over a buffer growing 64 KiB at a time. The measured cost of that is worse than the same volume spent on real commands: 64 MiB of unterminated header cost more CPU than 64 MiB of pipelined `PING`s, which at 14 bytes a command is 4.8 million commands actually answered.

So the two primitives take a `search_from`, and `Connection` keeps one per connection. A search that found nothing has proved the whole buffer holds none, so the next attempt resumes at the end of what it already walked and each byte is examined once per command rather than once per readable event. The position steps one byte back from the end rather than sitting on it, because a `\r` already buffered pairs with a `\n` that has not arrived, and resuming past that pair loses the header entirely -- the connection would then hang with nothing to show for it, which is a worse failure than the cost this exists to avoid. An inline line ends at a single `\n` and has no pair to split, so it resumes at the end.

What this does not do is bound the buffer. A client can still send an unterminated line forever and the read buffer still grows to hold it; that cap is the deferred feature listed among the deliberate differences below. This makes the growth cost linear rather than quadratic, which is a different fact from making it finite.

### Why Connection is a class

Keeping a raw socket in a dict keyed by its file descriptor works right up until something else needs to be tracked per connection. Four more things attach state to a connection later in this project -- rate-limit tracking, a follower link, buffer water marks, an incomplete-command deadline -- and each one would need its own parallel fd-keyed structure if `Connection` didn't already exist to hold it. It ships now, with fields nothing reads yet, so that structure exists once instead of getting rebuilt piecemeal.

### Why the three extra state slots are untyped

`rate_limit_state`, `replication_state` and `server` hold `None` here and are read and written only by the module that owns each one -- the third owned by `server.py` itself rather than by a module still to come. Giving any of them a real type would make `connection.py` -- the most foundational module in the project -- import the module that defines that type, and that module needs `Connection` back: an import cycle, in the one file nearly every other module in this project eventually imports. `server.py` already imports `Connection`, which is what makes the reverse import a real cycle for the third slot too, not only a future one.

### Why the connection's third slot carries a narrower contract than the other two

`connected_clients` is the only one of `INFO`'s five fields that is a fact about sockets rather than about the store or the process -- `redis_version` and `role` are constants, `used_memory` is a syscall reachable from anywhere, and the keyspace line comes from the store `INFO` already receives as an argument. Only the connected-client count needs the server itself, which is what the third slot, `server`, exists to reach: filled in `Server._on_accept` once a connection is registered and tracked, and cleared in `Server._close` before the socket closes.

What sets this slot apart from the two beside it is who reads it -- a command handler, in a different module from the one that fills it. A full attribute-and-method surface would let a handler reach as deep into `Server` as it liked, which is the same category of layering violation the store's own internals check exists to catch, just outside where that check looks. The contract is written down rather than enforced by a type: a handler may read the slot's object's named public attributes and nothing else -- no method calls, no underscore-prefixed names. `Server` grows a public `connected_clients` property rather than `INFO` reading a private `_connections` set, so the one fact this slot needs to expose is already shaped as an attribute read rather than a call. The slot is `None` for a connection driven with no socket at all -- this project's own convention for in-process use -- and `INFO` answers `connected_clients:0` there, a documented answer rather than a fallback hiding a bug.

### Why select() has a bounded timeout

The tasks that need to run on a schedule -- sweeping expired keys, writing a snapshot -- run right after `select()` returns, never on a clock of their own. An unbounded `select()` on a server with no client traffic would simply never return, so once those tasks exist, an idle server would never run them. The timeout is bounded to keep that from happening, and it doubles as the longest a stop signal has to wait before the run loop notices it.

### Why inline commands are supported

A bare `PING\r\n`, with no multibulk framing at all, parses as a command here, and now gets a real `+PONG` back like any other reply. That's what makes `nc localhost 6379` work as a demo with nothing installed beyond what a shell already has -- point it at the port, type a command, and get an answer in the same session. `telnet localhost 6379` does the same thing on a machine that has telnet, but macOS has not shipped one since 10.13, so there it is a package to install rather than something already on the box. Quoting works the way someone typing at a terminal expects, because that's the grammar a real server applies to the same line: `ECHO "a b"` is one argument with a space in it, `'` quotes as well as `"`, `\xHH` and the usual character escapes are understood inside double quotes, and a quote left open is a protocol error rather than a literal character.

Real Redis ships a companion load-generation CLI alongside `redis-cli`, and the first workload of its default run is exactly that unframed `PING` -- 50 connections all sending `PING\r\n` with no `*`/`$` around it. Accepting inline input is what lets that workload run here at all. The tool opens by asking for two configuration values in ordinary multibulk framing, both of them in a single write, which this server answers with two unknown-command errors in a single write back, and it carries on regardless, printing one warning; the multibulk `PING` workload that follows works too.

### Why the periodic tasks belong in server.py

The four periodic tasks driven off the `select()` timeout -- expiry sweep, snapshot interval, follower reconnect, slow-follower check -- belong in `server.py` rather than in `event_loop.py`. `event_loop.py` is kept to readiness dispatch alone: it knows the `Connection` class and three callbacks (`on_readable`, `on_writable`, `on_accept`) and nothing else. Putting the periodic tasks there would pull the store, persistence, the command layer, and eventually replication into the thinnest module in the project. None of the four is wired into the run loop yet.

### Why commands is a package

The command layer covers twenty-six commands across the string, list, and server/connection groups, each with its own arity check, type check, option parsing, and effect return. A single `commands.py` holding all of that would be a god object, so the command layer is split by type into its own package instead, with `registry.py` handling registration and dispatch.

### Why the kind tag is declared at the handler

A command's `read`/`write`/`other` tag is set through the same decorator that registers it, in `commands/registry.py`, rather than listed in a separate table somewhere. A table is a second place that can disagree with the handler it describes -- a rate limiter or a replication decision reads whichever one it was pointed at, and a command mistagged in the table looks correct at every other call site. Declaring the tag where the command is registered means the declaration and the handler are the same statement, so the two can't drift apart; an enum on top of that turns a typo in the tag into an error at the line that has it, instead of a value that silently matches nothing.

### Why one lookup answers every existence question

`Store.lookup()` is where a handler asks whether a key is there, and every handler that needs to know goes through it -- `SET`'s `NX` and `XX` conditions, `INCR` and `DECR`'s read-modify-write, every type check made by passing `kind=`, and every plain `GET` besides. A key past its deadline is deleted the moment this call finds it and reported as absent from there on, so the answer is the same no matter which handler asked or why. A raw `key in self._data` written anywhere else would skip that deletion and answer a question this server has already decided differently, with nothing downstream ever told the two disagreed. `DBSIZE`, `KEYS` and `INFO`'s keyspace line are the one deliberate exception to this rule, covered below.

### Why a list value is a `collections.deque`, never a Python `list`

`LPUSH` and `LPOP` both act on the head, and a Python `list` is O(n) per head operation because every remaining element has to shift down to close the gap. Measured on this machine: `list.insert(0, x)` at n=100,000 costs 50.90 microseconds, `deque.appendleft` costs 0.02 microseconds, and one whole `SET` through this server's own dispatch costs 0.70 microseconds -- so implementing the head push the `list` way would cost as much as 73 entire command dispatches at that size alone, growing without bound as the list grows further, against a `deque` push that stays a small fraction of one dispatch regardless of size.

The trade is not free, and the cost is visible on the other side of the same choice: `LRANGE` reads through `itertools.islice`, and `islice(deque, 0, 600)` measures 3.69 microseconds against 0.76 microseconds for the equivalent `list` slice -- a 4.9x constant factor on a command the standard benchmark invocation runs twice. It is taken anyway because the push-side penalty is unbounded in the size of the list while the range-side penalty is a constant bounded by the length of the range asked for. A `deque` also gives up O(1) random indexing, which no command here needs -- `LRANGE` walks a run in place, and nothing indexes a single element by position.

### Why `DBSIZE`, `KEYS` and `INFO` are the one path that bypasses `lookup()`

Routing any of the three through the expiry-aware `lookup()` fails on two separate grounds: it would turn an O(1) count into an O(n) scan, and it would have a read command delete every expired key it happened to scan past, queuing a `DEL` for each -- a count, a listing or a report mutating the keyspace it was only asked to describe. Only one of the two problems can be fully solved: any filter that answers correctly has to inspect every deadline, so `DBSIZE` cannot stay O(1) and also filter. What it gets instead is the cheapest available correct answer -- `len(_data)` minus the count of already-passed deadlines in the expiry index, which is linear in the number of keys carrying a TTL rather than in the keyspace as a whole, so a keyspace with few TTLs stays cheap however large it grows. `KEYS` is linear in the keyspace regardless, because it has to return every key that matches. All three live on `Store` itself -- `DBSIZE` and `INFO` both read `live_count()`, `INFO` alone also reads `expiring_count()` for its `expires=` figure, and `KEYS` alone reads `live_keys()` -- rather than as license for the command layer to read `_data` directly -- no module outside `store.py` touches it, and this exception is no different.

### Why `KEYS`'s glob is hand-written rather than `fnmatch`

The two were measured side by side on the same nine patterns against the same key sets -- the reference over the wire, `fnmatch.fnmatchcase` in this interpreter -- and they disagree on four. Three of the four are exact opposites of each other: `^` negates a character class on the reference and is an ordinary member of the class under `fnmatch`, and `!` is the reverse. A client asking this server for the complement of a set would, under `fnmatch`, receive exactly the set it meant to exclude -- the complement of the complement -- with no error anywhere to notice by. The fourth disagreement is backslash escaping: `fnmatch` has none, so `a\*b` matches `a*b` on the reference and matches nothing under `fnmatch`. Two further problems stand on their own regardless of what the reference does: `fnmatch` operates on `str`, against the `bytes` invariant this project holds everywhere else, and it memoises every translated pattern in a cache that lives for the process and is keyed by whatever a client sends it.

### Why deadlines are wall-clock and durations are not

`Store.now_ms()` reads `time.time()`, not a monotonic clock, and every deadline in `_expiry` is milliseconds since the Unix epoch -- what `PEXPIREAT` hands the store directly, and what `EXPIRE` and `PEXPIRE` convert their durations into before `_apply_expiry` ever sees them. A deadline two machines can agree on has to be a timestamp both read the same way, which is what a monotonic clock cannot offer: it reads faster and never jumps, but what it counts is an offset from an epoch that means something only to the process that started counting. A deadline recorded against that offset means nothing to a second server, or to this one after a restart, and the corruption stays invisible until exactly that moment.

### Why the integer grammar is hand-written

`parse_int64` checks a field byte by byte before it ever calls `int()`, because `int()` accepts several shapes the protocol does not: a leading zero (`011`), surrounding whitespace (`" 5"`, `"5 "`), an explicit sign (`+5`), a digit-group underscore (`1_0`), and a negative zero (`-0`) all parse cleanly under `int()` and are all refused here. The gap isn't cosmetic on the one path where a stored value comes back through this function: `INCR` and `DECR` reinterpret whatever `SET` last wrote as an integer, and left to `int()`, a stored `"011"` reads back as `11` and `INCR` hands back `12` -- silently accepting, on the way out, exactly the string real Redis refuses on the way in.

### Why a past-dated expiry deletes rather than schedules

`EXPIRE`, `PEXPIRE` and `PEXPIREAT` all resolve to an absolute deadline before `_apply_expiry` acts on it, and a deadline at or before now deletes the key on the spot instead of being written into `_expiry` for a later lookup to clean up. The two look identical here -- either way the key reads as gone -- but lazy expiry only runs when something looks the key up again, and with no active sweep yet, nothing guarantees that happens. Deleting on the spot means the `DEL` a follower needs ships with the command that caused it, rather than waiting on a lookup that may never come. A follower stuck with the other version would be holding a key its leader has already stopped considering real, with no `DEL` ever arriving to say so.

### Why a reply and its effect are different facts

A handler here returns reply bytes and a list of effects -- `Reply = tuple[bytes, Effects]` -- and every handler returns both, `PING`, `ECHO` and `HELLO` included, where the second element is always empty. What a client sees is not the whole of what a later feature needs to know happened: a `GET` that finds an expired key has to produce a deletion nobody asked for, with no write command anywhere in the request to carry it. That case doesn't go through a handler's own effects list either -- the key expired inside `lookup()`, which `GET` only called, so the `DEL` goes onto the store's own pending queue instead, which `server.py` drains once per dispatched command, ahead of the handler's own effects in whatever a follower would eventually apply. Both lists reach `server.py` and both are discarded there: nothing here consumes an effect yet, because nothing here replicates. The shape is built and exercised before it has a reader, so producing the fact correctly is already done on the day a follower needs it, rather than retrofitted onto handlers that never had to account for it.

### Why the last `LPOP`/`RPOP` off a list emits no `DEL`

`Store.remove()` deliberately appends nothing to the effects queue, which is what keeps the empty-container cleanup from doubling the replication stream. A follower applies `LPOP`/`RPOP` through its own dispatcher, exactly as the leader did, so the same emptying pop triggers the same cleanup against the follower's own copy of the list -- a `DEL` sent alongside the pop would be redundant, not corrective. The pair is idempotent, which is exactly why nothing breaks today and why a redundant `DEL` would go unnoticed: it would simply double the replication traffic on every list that empties, with no test able to tell the difference from a stream a leader and follower already agree on.

### Why the write path exists before any reply is large

Three commands exist and none of them touches a keyspace, but a reply can already be as large as `ECHO`'s own argument, and a socket can already refuse to take a large write in one call. Measured against a copy of this server whose only write path was a bare `socket.send()` with nothing behind it to catch what the kernel wouldn't take: 200,000 pipelined `ECHO` commands down one connection, with the client writing every request before it read a byte, which is what fills the kernel's send buffer the way a client that has stopped draining does. This server delivers all 200,000 replies whole on every run. The bare-`send()` copy delivered between 80,000 and 115,000 of them, the count moving run to run on the same workload, and the shape of the loss matters more than the count: one reply -- the one being written when the buffer filled -- arrives cut in half, and almost every reply after it is never transmitted at all, because a `send()` against a full socket raises `BlockingIOError` and writes nothing, so the discarded remainder is a whole reply rather than the tail of one. A write path that survives a partial write isn't an optimization added later -- it's the difference between a reply and a reply the client never sees, and it ships in the same commit as the first reply rather than waiting for a request large enough to make the gap obvious.

### Why the cap on a queued reply closes rather than throttles

A client that keeps asking and stops reading is the cheapest way to spend this server's memory. Replies queue in a per-connection buffer, and the cost is not paid in the bytes it takes to ask: one 64 KiB write holds a few thousand `GET`s -- about three thousand at a short sixteen-byte value, ranging from roughly one thousand at fifty bytes to nearly six at five -- every reply is buffered whole, and the value they all name was stored once. Measured with no limit set, 2,200 bytes of pipelined `GET` against a single 1 MiB key grew the process by tens of megabytes -- four orders of magnitude more than the request -- while the keyspace itself never grew at all. The exact figure is not worth quoting: it is resident-set size sampled from outside the process, and how much of a reply is held in the write buffer rather than absorbed by the kernel's own socket buffers varies with the platform and with the moment the sample lands. What does not vary is the shape, which is the whole reply set held at once. That is a different shape of problem from the `SET`-until-it-dies case described under Status, which costs a byte per byte.

`--output-buffer-limit` bounds it, and what it does when exceeded is the design. The obvious answer is backpressure: stop reading a connection whose replies are piling up, resume when they drain. It deadlocks, and the code that implements it looks correct. A client that writes every request before reading a byte -- the workload the write path section above is built around, and what a pipelining client library does -- fills the queue, has its own reads stopped, and then blocks in `send()` waiting for room that only its own reading would create. Both sides wait. Measured against a build with a 1 MiB mark and no other change: 200,000 pipelined `ECHO`s, five megabytes of requests written before the first read, and the client's `sendall()` never returns. So the limit closes the connection instead, as the reference does.

It is consulted twice, and both places are load-bearing. After a flush, because what a limit should measure is what the kernel would not take rather than what was queued a moment ago -- a reply larger than the limit that leaves in one `send()` costs nothing to hold. And inside the dispatch loop, because one `recv()` can carry thousands of commands and queueing every reply before the first send is exactly how a few kilobytes of request commit gigabytes: checked only after the batch, a 4 MiB limit was measured letting 104,597,124 bytes accumulate first. The in-loop check flushes before it judges, so a client whose replies the kernel keeps taking is never closed however deep its pipeline gets, and the peak is bounded to the limit plus one reply. What it does not do is wait: this is a hard limit in the reference's sense, and a hard limit closes a connection for holding too much, not for failing to read. A client that reads continuously but slower than the server produces is closed the same as one that stopped -- `redis-cli --pipe`, which reads concurrently by design, is disconnected here at `--output-buffer-limit 4096` by a hundred pipelined `GET`s of a single 50 KB value -- the shape matters and the sentence used to omit it, because alternating `SET`/`GET` pairs at the same value size drain between commands and never trip it, and redis-server 7.2.7 configured with `client-output-buffer-limit normal 4096 0 0` disconnects it too, logging that it overcame its output buffer limits. The reference pairs its hard limit with a soft one -- a lower ceiling that has to be held for some number of seconds before it counts -- which is what makes a merely slow reader survivable there. That is the half not built here, and it is why the default is off.

The default is 0, which disables it, because that is what the reference defaults to for an ordinary client and a server that disconnects where the reference does not is a divergence nobody asked for. Replication will need its own links exempted, on the reasoning that keeps them off the rate limiter: a follower that falls behind is not a client that has stopped reading.

### Why write interest turns off the moment the buffer empties

`event_loop.py` asks the selector whether a connection is writable only while that connection's write buffer is non-empty, and clears the request the instant a flush empties it. An idle, healthy socket is writable on nearly every pass, so a write request left registered against an empty buffer would have the selector reporting that connection ready again and again with nothing queued to send -- the loop would spend its time asking the kernel about a socket that has nothing to say. The selector's own mask is also the only place this fact is kept: a separate flag on `Connection` would be a second copy that can disagree with the selector, in either direction, with nothing around to notice when it does.

### Why an unknown command gets an error, not silence

`-ERR unknown command '<name>'` costs one write and leaves the connection open. Silence costs nothing to produce and is worse to receive: a client that gets nothing back cannot tell a slow server from one that will never answer, and has no way to distinguish "still working on it" from "doesn't understand this at all" -- it can only wait, or guess. An error reply lets a client's own retry and timeout logic run the way it was built to, on a connection that never had to be dropped over a single bad request.

### Why one exception boundary covers a whole connection

Every step of handling a connection's traffic -- reading, parsing, dispatching, writing -- runs inside the same `try`/`except` in `server.py`, reached from both the readable and the writable callback, rather than one boundary per callback. Two boundaries are two places to write a slightly different close path, and the failure that produces is invisible until a client happens to hit the one that's wrong: a bug that closes its connection cleanly when it surfaces on a read, and takes the whole process down when the same bug surfaces on a write. A single-threaded server has exactly one thread to lose, which is what makes this boundary mandatory rather than a defensive habit -- every other connection's traffic stops the moment an unhandled exception reaches the top of that thread. The boundary's own recovery is the second half of that: closing a connection can itself fail -- the flush, the deregistration and the socket close can each raise -- and a raise from inside the handler reaches the top of the thread just as surely as the original one would have. One `_abandon` answers for that, reached from the boundary and from the shutdown sweep alike, so there is one place that decides how a connection which cannot be closed is disposed of rather than one per caller.

### Twenty deliberate differences from real Redis

- An unknown command answers `ERR unknown command '<name>'`. Real Redis appends the first few arguments it received to that message; this server never does, and the argument list plays no part in it. That does not make this server's message the shorter of the two, which is the easy thing to assume: real Redis renders the name through a `%.128s` conversion and its whole reply tops out at 181 bytes however long the name was, while this server echoes the name whole and caps nothing. A 200,000-byte command name answers 181 bytes there and 200,025 bytes here. It is the only reply this server can be made to produce at an arbitrary size while it still has no keyspace to put anything in, and what bounds it is the missing request cap described under Status rather than anything in the message.
- `HELLO` with an argument other than `2` answers `NOPROTO unsupported protocol version`, whatever that argument is. Real Redis has two rules here that this server collapses into one: a non-numeric argument gets a different error naming a parse failure specifically, and `3` isn't an error there at all -- it's RESP3, a second protocol version a real server accepts, switching that connection to a different reply grammar. This server speaks RESP2 and nothing else, so `HELLO 3` is refused with the same message as `HELLO banana`, and there is one rule to remember rather than one rule plus two exceptions.
- `HELLO` takes the protocol version and nothing else. Real Redis also accepts `AUTH <username> <password>` and `SETNAME <name>` after it, so `HELLO 2 AUTH u p` answers `WRONGPASS` there and `ERR wrong number of arguments for 'hello' command` here. Neither option has anything to act on yet -- there is no authentication in this server, and no connection name to set -- and a client library that opens with `HELLO 2 AUTH ...` gets an arity error rather than an authentication one.
- `HELLO` counts its arguments before it looks at any of them. `HELLO x y` answers `ERR wrong number of arguments for 'hello' command` here and `ERR Protocol version is not an integer or out of range` there; `HELLO 2 BADOPT` answers that same arity error here and `ERR Syntax error in HELLO option 'BADOPT'` there. Real Redis parses the version first and then walks the options, so it names whichever one is actually wrong; this server takes a version and nothing after it, which makes every one of those shapes a wrong argument count before it is anything else. The more specific complaint is the one that never gets made.
- Commands that parsed successfully ahead of a malformed one in the same write lose their replies. `PING`, `PING`, then `ECHO "unterminated` sent as one write answers only `ERR Protocol error: unbalanced quotes in request` here, where real Redis answers both `PONG`s first and then the error. The parser reports the whole buffer's first failure rather than returning what it had already read, and the connection closes immediately either way, so the loss is bounded by whatever that one connection had in flight. Sent as separate writes, every command is answered normally on both servers. Changing this belongs with the pipelining work rather than here.
- A negative multibulk count is a protocol error. `*-1\r\n` gets `ERR Protocol error: invalid multibulk length` here and the connection closes; real Redis consumes any count of zero or less without replying and goes straight on to the next command in the same buffer. A negative *bulk* length inside a multibulk -- `$-1` -- is rejected by both, which is what makes this one easy to miss.
- A bulk body must be followed by `\r\n`. `*1\r\n$4\r\nPINGXX\r\n` declares four bytes and then supplies six, which this server refuses with `ERR Protocol error: unterminated bulk string`; real Redis advances past the body by its declared length and never inspects the two bytes after it, so it answers `PONG` and treats the stray bytes as an empty inline command. That error string has no real-Redis equivalent -- this server is the stricter of the two here.
- Every `\r` that ends a header must be followed by `\n`. Real Redis finds the `\r` and steps two bytes past it without ever looking at what the second byte is, so `*1\rX$1\r\na\r\n` and `*1\r\n$1\rXa\r\n` both parse there and answer `ERR unknown command 'a'`; this server refuses them with `invalid multibulk length` and `invalid bulk length` and closes. The same reading is what makes the entry above refuse `*1\r\n$1\r\na\rX`. Three positions, one rule: a lone `\r` is a terminator there and a framing error here, and this server is again the stricter of the two.
- A NUL byte ends an inline command line. `PING\x00X\r\n` runs `PING` here and everything after the NUL is dropped, which is what real Redis's own argument splitter would do with that line -- but real Redis never gets there, because it locates an inline command's end with a C string scan that stops at the NUL, so the line never looks complete and that connection stops answering permanently. The difference is invisible to any client that does not send a NUL.
- A NUL byte inside a *multibulk* command name is part of the name. `*1\r\n$4\r\nPI\x00G\r\n` answers `ERR unknown command 'PI\x00G'` here, the NUL sitting raw in the error body; real Redis builds the same message with a C string conversion that stops at the NUL, so it reports the command as `PI` and never sees the rest of it. Both servers answer and both keep the connection open, so the difference is only in what the message says was asked for.
- A NUL anywhere in multibulk *framing* is a protocol error here and silence there. `*1\r\n\x00\r\n`, `*\x001\r\n` and `*1\r\n$\x004\r\n` each get an error and an immediate close from this server -- `expected '$', got '\x00'`, `invalid multibulk length` and `invalid bulk length` respectively. Real Redis answers none of the three: it stops answering on that connection permanently, so a client sits waiting on a reply that will never come instead of reading an error and reconnecting. This is the same reasoning as the unknown-command entry above, applied to a connection that has to be dropped: something that says why beats nothing at all.
- A declared *bulk* length is never refused for being too large. Real Redis rejects a bulk length above `proto-max-bulk-len`, 512 MB by default, the moment it reads the header; this server accepts any length it can convert and then waits for a body that may never arrive. Nor is a line refused for running on without a newline, in any of the three places one can: real Redis gives up at 64 KiB on an inline command with `ERR Protocol error: too big inline request`, on a multibulk count with `ERR Protocol error: too big mbulk count string`, and on a bulk length with `ERR Protocol error: too big bulk count string`, and this server keeps buffering in all three. Both are the wire-facing half of the missing request cap described under Status, and they are the one entry on this list that is a deferred feature rather than a preference -- the cap ships with the flag that configures it.
- A bulk element's type byte is checked before its header line is complete. `*1\r\nX` answers `ERR Protocol error: expected '$', got 'X'` here the moment the `X` arrives; real Redis searches for the terminator first and says nothing until the line ends, then answers the same error. Byte zero cannot retroactively become `$`, so the verdict is identical either way and only its timing differs -- but it differs on the wire, and refusing a malformed byte the moment it arrives rather than waiting it out is the rule this server follows elsewhere.
- `EXPIRE`, `PEXPIRE` and `PEXPIREAT` register with arity exactly `3`. Real Redis 7 takes `-3` for this family, because it accepts `NX`, `XX`, `GT` and `LT` after the key and the time; this server accepts none of those four, so there is no minimum to leave room for -- `EXPIRE k 10 NX` answers `ERR wrong number of arguments for 'expire' command` here, where a real server would parse the option by name and act on it or refuse it. The exact arity says plainly what accepting no options would otherwise leave a reader to infer.
- `DBSIZE` and `INFO`'s keyspace count filter logically-expired keys. The reference filters in `KEYS` and not in the other two: with two logically-expired keys resident and the active expiry cycle disabled, `DBSIZE` answers `3`, `INFO keyspace` answers `db0:keys=3,expires=2`, and `KEYS *` returns only the one live key. This server makes all three agree, because two introspection commands disagreeing about the same number is worse than either answer alone.
- `LPOP` and `RPOP` take a key and nothing else. The reference accepts an optional count -- `LPOP k 2` on a three-element list returns two elements and leaves one -- and the count changes the reply type from a bulk string to an array. Here it is a wrong-number-of-arguments error, matching this server's own precedent of exact arities over minimums that silently ignore a trailing option.
- `FLUSHALL` takes no arguments. The reference answers `+OK` to `FLUSHALL ASYNC` and `FLUSHALL SYNC` and `-ERR syntax error` to anything else. This loop is single-threaded, so the two options would name the same operation; `FLUSHALL ASYNC` here is a wrong-argument-count error.
- `CONFIG GET <param>` is a stub returning the parameter and an empty string, for every parameter. It reproduces the reference's answer for `save` byte for byte, which is the shape the standard benchmark actually depends on; it diverges for `appendonly` (the reference answers `no`) and for an unknown parameter (the reference answers an empty array).
- `INFO` reports a fixed, small field set -- `redis_version`, `connected_clients`, `used_memory`, `role`, and the keyspace line -- with no persistence fields and no uptime. Uptime is absent deliberately: it would be the first duration measured in the command layer, and every deadline in this server is absolute wall-clock time.
- `redis_version` reports this project's own version, `0.1.0`, not the reference's. The field name is the reference's because tooling reads that key; the value is this server's because it is not `redis-server 7.2.7`, and saying so would make the one field a client trusts the one field that lies.
